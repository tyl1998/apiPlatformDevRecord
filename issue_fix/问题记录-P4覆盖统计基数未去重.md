# 问题记录 — P4 覆盖统计基数未按 path 去重（仓库用例树）

## 现象

仓库用例页（`/repo-cases`）的覆盖读数 `已覆盖/接口总数` 偏低：用户反馈同一接口被数成
多个。典型触发形态（同一项目内、同 method）：

- `{{baseUrl}}/users/:id` 与 `{{baseUrl}}/users/{id}` 各一行（import 冲突键是**精确
  URL 字符串**，`:id` 与 `{id}` 判为不同）；
- `{{baseUrl}}/users/{id}` 与 `{{host}}/users/{id}`（不同变量前缀，同形状）；
- `/users` 与 `/users/`（尾斜杠；切段时被吃掉，匹配形状相同）；
- import 用 `create` 策略重复导入同一份清单（精确串相同的行也会再插一行）。

例：登记 10 条接口、其中 3 条被重复登记成 2 行 ⇒ 分母 13；上报用例挂到每形状的其中
一行 ⇒ 分子最多 10，覆盖率 10/13 而不是 10/10。

## 根因

`routes/ingest.ts` 的覆盖统计里 `endpoint_total` 是 `COUNT(*) FROM endpoints`——数的是
**行**，把上面所有「同行不同串」的重复行各计一次。而 `lib/ingestPath.ts` 的
`buildEndpointMatcher` 是确定性的：同形候选里**字面段更多者胜、全同则登记在前者胜**，
上报的用例关系永远只落到其中一行。于是分母按行数虚高、分子按行数最多 1，覆盖率被
系统性压低。

配套缺口：手工建接口（`POST /endpoints`）对 `(method, 形状)` 没有任何查重，import 的
冲突键只比对精确 URL 字符串——重复行可以自由产生，统计口径却假设了「一行 = 一个接口」。

## 修法

读时去重（用户 2026-08-30 选定），不动存量数据、不加迁移：

- `lib/ingestPath.ts` 新增 `coverageShapeKey(method, path)`：`METHOD /users/{}`，与
  `comparableTemplate` 共用同一等价关系（占位符无名化），并把这个共用关系写进两边
  注释——等价关系要变必须一起变。方法名进键（GET/POST 同路径是两条接口）。
- `routes/ingest.ts` `/repo-cases` 的覆盖统计：
  - 分母 `endpointTotal` = `loadEndpointShapes` 归一后的 **distinct 形状数**；
  - 分子 `coveredEndpointTotal` = 挂了 active 用例关系的接口行映射到形状后的
    **distinct 形状数**（同形多行里任一行挂了用例即算覆盖）；
  - 用例总数 / 软删数 / 未归位数不变；`/dashboard` 的 coverageRate 一字不动
    （边界 2，接口模式的行口径维持现状，留给统计重做那一轮）。

树上（接口行列表与分页）仍是**行口径**：重复登记时行数 ≥ 形状数，两处对不上是
登记侧该清理的信号，统计不再替它圆谎。

## 状态

已修（2026-08-30）。未做写时唯一约束（`path_shape` 列 + `UNIQUE(project_id, method,
path_shape)`），用户选定先读时去重；若后续重复登记高频出现再补约束与迁移。
