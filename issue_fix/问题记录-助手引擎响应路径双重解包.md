# 问题记录：助手引擎响应路径双重解包（建会话必失败）

- **日期**：2026-09-14
- **状态**：已修复（当日，engine.ts `callJson` 重写）

## 现象

系统管理 → 助手 provider → 测试连接，任何配置正确的平台都报
`502 "assistant upstream error: assistant upstream did not return a conversation id"`。
Nuwax 本地实例（agentId=38）经 curl 直连完全正常（建会话返回
`{"code":"0000","data":89}`），但经平台测试必失败。

## 根因

`lib/assistant/engine.ts` 的 `callJson` 在返回前**预剥了一层 data**
（`return parsed?.data ?? parsed`），而协议配置里的「会话 id 响应路径」
（如 `data`）是**根相对**设计的——于是 `{"code":"0000","data":89}` 先被剥成
数字 `89`，再对数字取 `.data` 点路径 → `undefined` → 「没返回会话 id」。
历史接口的 `messages` 路径同款隐患（独立实现了一份读腿，同样预剥）。

设计错误在于：**信封剥层与路径配置抢了同一件事**。路径配置的存在意义就是
「响应结构因平台而异，由管理员声明」——引擎再偷偷剥一层等于把「Nuwax 有
data 信封」这个平台特例焊死在代码里，配置反而说了不算。

## 修法

`callJson` 返回**响应根对象**，删掉 `?.data` 预剥；建会话的 `conversationId`
路径、历史接口的 `messages` 路径都改为根相对取值（`engineHistory` 里独立那份
读腿同步修正）。注释里写明纪律：**引擎不解信封，路径怎么写就怎么取**。

## 验证

- curl 直连上游：建会话 / 发消息 SSE / PROCESSING 工具行均正常（排除上游因素）；
- 修复后经平台测试连接：建会话 ✓ → 工具行 ✓ → token 流式 ✓；
- 前后端 `pnpm check` 通过。
