# 测试计划详情 500：LATERAL 参考列 SQL 括号错位

- 日期：2026-09-09
- 模块：apitest-server（`src/routes/testPlans.ts` 详情路由的自动化参考列查询）

## 现象

打开任一测试计划的详情页报「读取计划列表失败」，接口 `GET /api/v1/projects/:id/test-plans/:planId` 500；列表页本身正常（`GET /test-plans` 200）。API 日志（`.dev-logs/api.log`）两条完整取证：

```
err: syntax error at or near "ORDER" (SQLSTATE 42601, position 1689)
    at apitest-server/src/routes/testPlans.ts:243 (references 查询)
```

position 1689 精确落在 `ORDER BY at DESC NULLS LAST` 的 `ORDER` 上。

## 根因

只读自动化参考列的 LATERAL 子查询括号错位，多写了一行 `) u`：

```sql
LEFT JOIN LATERAL (
  SELECT raw, at FROM ( …case 分支… ) u1
  UNION ALL
  SELECT raw, at FROM ( …flow 分支… ) u2
  UNION ALL
  SELECT raw, at FROM ( …repo_case 分支… ) u3
) u                                  ← 把 LATERAL 提前闭合，别名 u
  ORDER BY at DESC NULLS LAST
  LIMIT 1
) best ON true                       ← 悬空的多余右括号
```

三个分支各自的 `SELECT raw, at FROM (…) uN` 是自封闭的完整 SELECT，UNION 起来就是 LATERAL 的全部本体；`) u` 一步把深度打回 0，`ORDER BY / LIMIT` 掉到外层，`) best ON true` 成了无配对的右括号（全串计数 -1）。PG 语法层面报错点在 `ORDER` 而不是多余的 `)`：`LEFT JOIN` 的右侧表引用解析完后文法期待 `ON`，先撞上的是 `ORDER`，所以报错位置停在 ORDER 上（用最小复现确认过，报错词与位置同形）。

代码注释本身写的是对的（「ORDER BY at DESC LIMIT 1 在 LATERAL 内部……写在外面是……语法错误」）——实现与注释不符。

## 修法

删掉 `) u` 一行：`ORDER BY at DESC NULLS LAST / LIMIT 1` 直接收在三个 UNION 分支之后（对整个 UNION 结果排序取一，正是「每项各自取最新一条」的既定语义），`) best ON true` 闭合 LATERAL。已用改后文件里的 SQL 原文对 dev 库直跑验证：括号深度归零、解析执行通过（哑 planId 0 行属预期）。

伴生观察（未改）：详情页加载失败态复用了列表的 i18n 键 `testPlans.loadFailed`（文案「读取计划列表失败」），所以详情挂了报的也是「列表」——本次修复后该文案不再出现，键的措辞留待后续有需要再拆。

## 状态

已修（`apitest-server/src/routes/testPlans.ts`，一行删除）。api 进程是 `tsx watch`，保存即热重载，无需手动重启；待用户刷新详情页复验。
