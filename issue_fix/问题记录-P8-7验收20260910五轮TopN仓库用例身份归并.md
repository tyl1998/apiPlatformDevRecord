# P8-7 验收五轮：失败 TopN 仓库用例维身份归并缺陷（同用例两种 key 形态拆两行）

> 2026-09-10，P8-6/P8-7 验收第五轮（用户反馈④「失败 topN 仓库用例为什么跳转到
> 具体某一个执行记录上了这样感觉很奇怪」——排查下钻设计时发现同维还有一个
> 身份归并缺陷，一并修）。

## 现象

失败 TopN 切「按仓库用例」维时：

1. **下钻落点奇怪**（用户原话）：点某条用例行跳到 `pipeline-runs/:runId`——组内
   「最近一次失败」的那一次 run 的详情页。等于替用户挑了一次执行，看不到这条
   用例的整体失败情况。
2. **同一用例拆成两行**（排查时发现）：`test_case.auth.test_login_invalid#test_…`
   与 `test_case/auth/test_login_invalid.py::test_…` 在榜上是两行——它们是同一条
   用例的两种 `guessed_case_key` 形态（dev 库实测同窗各 30/10 次失败，归并后
   应为一行 40 次）。

## 根因

P8-7 落 `repo_case` 维时按**裸 `guessed_case_key`** 分组，且 refId 取「组内最近
一次失败 run」供下钻直跳：

- `guessed_case_key` 有两种形态（allure 的 `pkg.Mod#test` 与 pytest 的
  `pkg/Mod.py::test`，参数化用例另带 `[params]` 后缀）——`ingest.ts` 匹配
  `repo_test_cases` 时早有归一尺（去参数化后缀直等 + `#` 形态折算 `.py::`），
  TopN 维没有用它，两种形态各成一组；
- refId 直跳 run 详情是 P8-7 的下钻设计（「失败用例行就在里面」），但一次 run
  只回答「那一次怎么失败的」，不回答「这条用例最近怎么样」。

## 修法

`stats.ts` 的 `repo_case` 维 SQL 重写（已 psql 实跑验证）：

- **身份归并**：`LEFT JOIN repo_test_cases c`（匹配条件与 `ingest.ts` 同一把尺），
  分组键 `COALESCE(c.case_key, regexp_replace(guessed_case_key, '\[[^\]]*\]$', ''))`
  ——匹配上的用规范 case_key，未匹配的退去参数化裸 key（NULL key 仍天然排除）；
  榜行 `name` = 该规范 key（dev 库实测两形态 30+10 → 40 合一行）；
- **下钻改用例树**：不再返回 refId，前端 `drillTopRow` 的 `repo_case` 分支改跳
  `/repo/tree?keyword=<规范 case_key>`——用例树是这条用例的资产页（最近任务列 +
  抽屉全部历史 run），keyword 检索命中 name/case_key/文件路径三入口；Flaky 榜的
  两条仓库腿（上报/任务）同款落点。

配套：同轮 flaky 增仓库任务腿（runner）时，新腿的序列分区键用同一把规范尺——
两种 key 形态折成一条用例，序列才不会断成两截各数各的（见计划十二章
「验收反馈五轮」⑤）。
