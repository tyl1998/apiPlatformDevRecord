## #1 明文记录开关对「无环境」执行失效

**发现阶段**：实现复查（`loadEnvironment` 无环境分支）。

**现象**：项目开启「明文执行记录」后，凡是不绑定环境的执行（接口/用例/流程步骤未选择环境），
执行记录仍被脱敏，开关看起来「部分生效」。

**根因**：开关存在 `project_settings`，而 `loadEnvironment` 在 `environmentId` 为空时
提前返回 `{ storePlaintext: false }`，根本没有读 `project_settings`。明文标志是**项目级**的，
却只对「带环境的运行」生效。

**修法**：无环境分支也查询一次 `project_settings.store_plaintext`；带环境路径保持
LEFT JOIN 单查。

**状态**：已修复（`apitest-server/src/lib/run.ts`）

## #2 明文记录开启后「替换当前请求」恢复真实 Authorization 头

**发现阶段**：明文记录开启后的交互边界复查。

**现象**：明文项目里某次带认证的执行，快照 `Authorization` 为真实凭据而非 `***`；
点「替换当前请求」时，`loadRequest` 只过滤值为 `***` 的头部，于是把真实 `Authorization`
原样恢复到请求头编辑区，与认证页签配置并存。

**根因**：恢复逻辑以「快照一定被脱敏为 `***`」为前提（见 `EndpointWorkspace.tsx`
`loadRequest` 注释）；明文开关打破了这个前提，敏感头部不再被过滤。

**修法方向**：`loadRequest` 除 `***` 值外，再按敏感头名（`authorization` /
`proxy-authorization` / `x-api-key` / `cookie`）过滤，让认证页签保持唯一凭据来源。
运行时认证注入本就会覆盖同名 header，当前行为不致发错请求，但编辑区会显示一份
冗余凭据，容易误改。

**状态**：待确认（当前行为已随验收通过；修复与否待产品确认）

## 附：非 Bug 的已确认决策（2026-08-15 评审）

以下为讨论确认、且**已按确认实现**的模型决策，不是缺陷，记录于此便于核对：

- **认证独立成页签而不是平铺进 Body/Header**：Bearer/Basic/API Key 最终只落为
  header/query，但独立结构化字段是掩码语义（Spec 4.6）、Basic base64 自动生成、
  cURL/OpenAPI/Postman 无损导入导出、执行快照不回填凭据、以及未来 OAuth2/JWT
  自动换 token 的前提。当前 `apiKey` 支持 header/query，暂不扩 body 位置。
- **项目级「明文执行记录」开关默认关**：开启后该项目执行记录的请求/响应快照不再脱敏，
  环境密钥经 `{{var}}` 解析出的明文会随记录对项目内可读执行记录的人（含 viewer）可见，
  这是显式取舍，由项目管理员在「环境管理」页头部开关开启。
- **认证页签变量补全**：Bearer Token、Basic 用户名/密码、API Key 的 key/value 均接入
  `VariableField`（`{{` 触发、按环境/内置变量分组、密码框保持 `type="password"`）。
