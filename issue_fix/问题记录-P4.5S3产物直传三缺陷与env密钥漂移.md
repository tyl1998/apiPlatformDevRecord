# 问题记录 — S3 产物直传链路三缺陷（含 .env 引入的密钥漂移）

日期：2026-09-04 · 阶段：P4.5-7 产物对象存储（MinIO/S3 驱动接入本地验证）

## 背景

为本地验证 s3 驱动，`apitest-server/compose.yaml` 新增 MinIO 服务（9000 API / 9001 控制台，
`minio_data` 卷，bucket `apitest-artifacts`），并在 `start.sh` 增加「存在才 source
`apitest-server/.env`」的加载层（此前三个进程只读 `process.env`，`.env` 文件从未被消费）。
接入后一轮 CI 任务触发暴露三处缺陷。

## 缺陷一：.env 占位值引发加密密钥漂移，claim 连续 500

### 现象

- 触发 CI 任务后 run 永远 `queued` / `cancelling`，执行页无日志流；
- Runner 日志循环 `claim failed: data source credentials could not be decrypted; retrying`；
- API 日志 `POST /runner/claim` 连续 500（claim 的组装分支只回错误信息不打日志，定位靠 Runner 侧报文）。

### 根因

`.env` 从 `.env.example` 复制，占位值随 source 进入进程 env：

1. `DATA_SOURCE_ENCRYPTION_KEY=replace-with-...`（base64 解出 36 字节）→ `crypto.ts` 直接抛
   `must decode to exactly 32 bytes`；
2. 清空成 `JWT_SECRET=` 后又暴露两处「空串 ≠ 未配置」的代码缺陷：
   - `index.ts` `process.env.JWT_SECRET ?? "change-this-in-production"` —— 空串原样传给
     `@fastify/jwt`，启动即 `AssertionError: missing secret`；
   - `crypto.ts` 回退密钥 `sha256(process.env.JWT_SECRET ?? "apitest-local-data-source-key")`
     —— 空串的哈希 ≠ 历史回退密钥，`git_credentials` 里用旧 dev 密钥加密的 SSH 凭据解不开
     （AES-GCM 认证标签失败 → `could not be decrypted`）→ JobSpec 组装失败 → claim 500。

### 修法

`index.ts` 与 `crypto.ts` 统一改为 `process.env.JWT_SECRET?.trim() || 回退值`：空串与未配置
同义，dev 回退密钥与库内历史加密数据重新对齐。生产语义不变（显式配置优先生效）。

### 状态

已修复，claim 恢复正常（实测凭据可解，任务正常领取执行）。

## 缺陷二：s3 驱动 `uploaded_at` 永不落，产物列表为空、报告解析失败

### 现象

切 s3 驱动后，allure-results.zip 成功直传 MinIO（bucket 内可见对象），但：

- 报告页「产物为空」「报告解析失败」；
- `artifacts` 行 `storage_driver='s3'` 且 `uploaded_at` 恒为 NULL。

### 根因

fs 驱动的 `uploaded_at` 由它自己的直传端点回写（`PUT /runner/artifacts/:id/upload` 收完流
`UPDATE artifacts SET uploaded_at = now()`）；s3 驱动的 pre-signed PUT 直连对象存储，**平台
侧没有任何等价的落点**。而产物列表、报告装载（`findReportArtifactRow`）统一按
`uploaded_at IS NOT NULL` 过滤——行永远不可见，`loadRunnerReport` 把报告视图降级为 null。

### 修法

补齐协议闭环（对齐「fs 的 PUT 端点自己回写」的语义，s3 由 Runner 确认 + 服务端核实）：

- `objectStore.ts`：`ObjectStore` 接口新增 `objectExists(key)`——fs 走 `stat`，s3 走
  `HeadObject`（元数据级查询，不代理字节流，不违反边界 14）；
- `runners.ts`：新路由 `POST /runner/artifacts/:artifactId/uploaded`——鉴权同其它
  runner 接口；服务端 `objectExists` 核过才回写 `uploaded_at`（不核就写等于把判据交给
  客户端的嘴）；对象不存在回 409；已上传幂等回 ok；fs 驱动同样幂等（协议不按驱动分叉）；
- Runner `client.ts` 新增 `confirmArtifactUploaded()`，`uploader.ts` / `reportBundle.ts`
  在直传成功后调用——best-effort：失败记日志，不把已成功的上传改判失败。

存量兼容：fs 驱动上传后 confirm 幂等；旧 Runner（不发 confirm）在 fs 驱动不受影响，
s3 驱动需要新 Runner。

### 状态

已修复并验证（对象入 MinIO、行落 `uploaded_at`、报告视图正常解析）。历史遗留的一行
（对象已在桶内、`uploaded_at` 为 NULL）已按「核过存在再补」手工对齐。

## 缺陷三：`/ingest` 500 — INSERT 列数与占位符错位

### 现象

任务执行成功，但 SDK 上报持续 500：`INSERT has more target columns than expressions`
（`ingest.ts` 的 `ingest_runs` upsert）。

### 根因

`INSERT INTO ingest_runs (…15 列…) VALUES ($1..$14)`——`finished_at` 缺占位符（`$13::jsonb`
对应 `warnings` 的位次实际后移一位，参数数组 15 个但 SQL 只认 14 个）。迁移 049 折形改造
（幂等键两列化）时改列清单漏了占位符列表。

### 修法

占位符补齐 `$15`，与 15 列、15 参数一一对齐。

### 状态

已修复，`/ingest` 200、上报记录与执行索引正常落库。

## 备注

- MinIO 本地接入时 s3 endpoint 用 `http://localhost:9000`（进程档 Runner 与 API 同机可达）；
  容器档任务的 Runner 在容器网络内，需换 `host.docker.internal` 或 compose 服务名——这是
  endpoint 全局单值的已知约束，容器档启用时再处理。
