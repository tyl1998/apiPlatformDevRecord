# 问题记录：助手凭据通道两缺陷（2026-09-16，P9-8 收尾自查）

> 发现方式：P9-8 收尾走查「上游异常 + 门槛 2/12 可见性」时逐条读代码发现，非用户
> 实测。两处都在**用户级凭据**这条路上，一处是明文 Key 可落库回显，一处是解密失败
> 冒成 500。本文按 现象 / 根因 / 修法 / 状态 归档。

## ① `params` 通道能装下 secret 项：明文 API Key 落库并回显

### 现象

门槛 12 要求「apiKey 写库即密、接口只回已配置」，但这条请求能打破它：

```bash
curl -sX PUT localhost:3000/api/v1/assistant/my-agents/<providerId> \
  -H "Authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"params":{"agentId":"26","apiKey":"ak-plaintext"}}'
```

- `assistant_user_agents.params`（明文 jsonb 列）里出现 `"apiKey": "ak-plaintext"`；
- 下一次 `GET /api/v1/assistant/my-agents` 把它原样回给前端（`mapAssistantUserAgent`
  回 `params`）；
- 链路照常可用：`toRuntimeAgent` 先铺 `params` 再叠解密后的 `secrets`
  （`providers.ts:32-36`），所以明文那份一样能满足 `{{user.apiKey}}` 模板——**不会
  报错，静默生效**，因此更不容易被发现。

### 根因

`routes/assistantUser.ts` 的 PUT 里，两条通道的校验不对称：

- `params` 循环只验 `schemaKeys.has(key)`——**键来自模式即可**，没有排除
  `secret: true` 的项；
- `secrets` 循环有对应的一半（`!defined.secret` → 400 `not a secret field`）。

模式（`user_params`）本身就带着 `secret` 标志，判据是现成的，只是漏用了。

### 修法（2026-09-16）

- `assistantUser.ts`：PUT 里补一个 `secretKeys` 集合，`params` 循环命中即
  `400 / 1001 param "<key>" is a secret field: send it in "secrets"`；注释写明
  为什么（params 是明文列且只读回显，加密承诺从这里破）。
- 数据面：`params` 是**整份替换**（PUT 语义），用户下次保存就把残留的明文项清掉；
  项目未上线，不做回填迁移（照 AGENTS.md 的数据兼容口径）。
- 演练清单把它固定成一条回归（`drill/README.md` 第三节第 4 项）。

## ② 凭据解密失败冒成 500（应为 503/2005「去重填」）

### 现象

`DATA_SOURCE_ENCRYPTION_KEY` 换过（或 `.env` 占位值进 env 导致派生密钥漂移）之后，
任何走凭据的助手请求都能拿到一个 Fastify 500 与一段无指向性的内部错误；用户不知道
该做什么。

### 根因

`toRuntimeAgent`（`providers.ts:29-42`）在 `decryptSecret` 抛错时**直接把异常放出去**
（函数注释本身写着「按 agent 不可用抛清楚」，但没有任何路由接住）：

- `GET/POST /assistant/conversations`、`…/message`、`…/stop`、`…/messages` 都是
  `await loadEnabledDefaultUserAgent(...)` / `loadUserAgentForProvider(...)` 裸调用；
- `POST …/my-agents/:providerId/test` 的 `toRuntimeAgent(existing.rows[0])` 同样裸调；
- 于是 500（内部错误），而不是「重新填一次凭据」的指引——处置动作其实与
  「未配置」（503/2005）完全一致：去抽屉设置卡重填。

### 修法（2026-09-16）

- `routes/assistant.ts`：新增 `loadResolvedDefaultAgent(reply, userId)`——统一取
  「我的默认 agent」，解密失败时记服务端日志（部署级线索）+ 回 `503 / 2005`
  （`assistant credentials could not be read: re-enter your agent settings`）；
  五处闸门改调它。`resolveConversationEndpoints` 里读会话归属凭据的那一处同款
  catch，返回同一条错误串。
- `routes/assistantUser.ts`：测试连接路由的 `toRuntimeAgent` 加 catch → `503 / 2005`
  同句；不再静默降级成空凭据去打上游（那只会换来一个更难解释的上游 401）。
