# P4.5 迁移 045 后 /ingest 全量 500（c1f4d1ba 一次都没上报）

## 现象

2026-09-03 用户报告：最新执行的 commit `c1f4d1ba38d871dc6468d20cfd5e59b2aa7aa497`
（任务 run #17–#21，共 5 次）在「上报记录」页一行都没有——`ingest_runs` 里最新一行
还是 2026-09-02 的 `493d7b2e`。CI 任务本身全部 success/failed 正常落库。

证据在 run 21（success）的日志 warnings summary 里：

```
RuntimeWarning: apitrack could not report this run to http://localhost:3000/ingest
(HTTP 500: {"statusCode":500,"code":"55000","error":"Internal Server Error",
"message":"ON CONFLICT does not support deferrable unique constraints/exclusion
constraints as arbiters"}); the test result is unaffected
```

## 根因

迁移 045 把 /ingest 的幂等键建成了 `DEFERRABLE INITIALLY DEFERRED`：

```sql
ALTER TABLE ingest_runs ADD CONSTRAINT ingest_runs_commit_dedup_key
  UNIQUE (repository_id, commit_sha, ci_run_id)
  DEFERRABLE INITIALLY DEFERRED;
```

而 `src/lib/ingest.ts` 的插入语句（按 commit 折行合并的核心）是：

```sql
INSERT INTO ingest_runs (…) VALUES (…, '', …)
ON CONFLICT (repository_id, commit_sha, ci_run_id) DO UPDATE SET …
```

PostgreSQL 的 `ON CONFLICT` 仲裁器必须是**不可延迟**的唯一约束——`DEFERRABLE` 的
约束不能当 arbiter，语句直接报 SQLSTATE 55000。045 上线（03:11）之后的每一次
`POST /ingest` 都在事务里撞这条错误、整个回滚 500。

它没有被第一时间发现的原因有两层：

1. **SDK 的纪律把故障吞成了 warning**（`reporter.py`：「上报失败不动退出码、只
   warning」——这条纪律本身是对的），于是 CI 全绿，唯一线索在日志的 warnings
   summary 里；
2. 上报不进库的连带后果是 `completePipelineRun` 按 `(project, commit)` 反查
   `ingest_runs` 拿不到行，`pipeline_runs.ingest_run_id` 全为空——但那是「留空」
   而不是报错，界面上只是「缝合没发生」，没有任何红字。

## 修法（迁移 048）

```sql
ALTER TABLE ingest_runs DROP CONSTRAINT IF EXISTS ingest_runs_commit_dedup_key;
ALTER TABLE ingest_runs ADD CONSTRAINT ingest_runs_commit_dedup_key
  UNIQUE (repository_id, commit_sha, ci_run_id);
```

不带 `DEFERRABLE` 即 NOT DEFERRABLE，`ON CONFLICT` 可以用它做仲裁器。

- 045 的 `DEFERRABLE` 从来没有消费者：唯一想用延迟检查的场景是「事务里先 DELETE
  再 INSERT 同键」，而 /ingest 事务没有这个形状（合并走 ON CONFLICT，旧行删除只
  发生在 045 迁移自己的 DO 块里）。
- 幂等性不靠 DEFERRABLE：折形键 `(repository, commit, '')` 的插入值恒为 `''`，
  冲突判定与行上真值无关，即时检查语义与折行口径完全一致。
- 前向修正是新文件（045 已 applied 不可改）；新库两个迁移连跑的净效果 =
  045 的合并逻辑 + 一个正确的键约束。
- 验证：dev 库 `condeferrable = f`；同形状的
  `INSERT … ON CONFLICT (repository_id, commit_sha, ci_run_id) DO UPDATE` 在事务里
  跑通（随即 ROLLBACK，不留测试数据）。

**边界说明**：`pnpm check` 只是类型检查（迁移是纯 SQL，无类型面）；按项目规则未
重启服务、未做端到端验证——下一次同 commit 的 CI 执行即为真实复验（预期：
`ingest_runs` 出现 `c1f4d1ba` 的一行、`ci_execution_count` 从 1 开始累计、
run 行回填 `ingest_run_id`）。
