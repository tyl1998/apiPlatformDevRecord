# P4.5 仓库执行上报分支为空

## 现象

「纯测试」任务执行后 SDK 正常上报（前一轮产物链路修复后 `[apitrack] reported to
http://localhost:3000/ingest` 已出现），但上报记录里 **branch 恒为空**，行上带着平台警告：

```
run.branch is empty; this run can never take part in delete reconciliation
```

删除对账的第二道闸门（`branch = repositories.tracking_branch`）永远过不了。

## 根因

Runner 的 clone 形状是 `git init` + `git fetch --depth 1 <url> <ref>` +
`git checkout --detach FETCH_HEAD`（`clone --branch` 不收 commit sha，detach 是唯一能
同时覆盖分支/tag/sha 的形状）——workspace 处于 **detached HEAD，没有任何本地分支**。

SDK 的 `detect_branch()`（`apitrack/config.py`）先读 `APITRACK_BRANCH` 等环境变量（平台
没注入），再退到 `git rev-parse --abbrev-ref HEAD`——detached 时返回字面量 `HEAD`，SDK
按设计宁可回空串也不猜（取错与取空同样不对账，都安全，见其 docstring）。

而平台**明明知道**这次跑的 ref：`pipeline_runs.git_ref` 来自任务配置（`main`）。与
`APITRACK_GIT_URL` 同一条根因——clone 形状刻意不落地 git 元数据，平台又不把已知事实
交给 SDK。

## 修法

`lib/jobSpec.ts`：`sdk_ingest_enabled` 时注入第五件 `APITRACK_BRANCH = run.git_ref`
（SDK 的 env 优先级第一）。ref 形如 commit sha（7–40 位十六进制）时不注入——sha 不是
分支名，报上去只会让上报记录的分支列显示一个假分支；不注入与空串同样安全。

Runner 侧零改动（env 随 JobSpec 下发）。

## 状态

已修复（server 一处，`tsx watch` 已自动重载）。原预期「下一次执行起 branch 应为
`main`，删除对账闸门二可通过」——**已随 2026-09-03 P4.5 验收通过关闭**。注意：对账
闸门一（`is_full_inventory` 且 inventory 非空）另受 xdist 多进程上报问题影响，见
`问题记录-P4.5SDK在xdist多进程下重复上报.md`（亦已随验收关闭）。
