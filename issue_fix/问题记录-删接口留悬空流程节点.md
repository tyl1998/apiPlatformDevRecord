# 删接口留悬空流程节点，流程再也保存不回去

2026-10-21 · 状态：**已修复（B 方案，待用户验收）**

## 现象

在带流程引用的接口上执行删除后，再打开引用它的流程点保存，报：

```
a node references an endpoint that does not exist in this project
```

dev 库实测有 3 条流程共 8 个请求节点处于这个状态（`endpointId` =
`0a85c957-a276-4e3a-a550-72ca31584451`，该接口与来源用例均已删除）：`测试`、`测试流程2`、
`测试调试删除`，节点为 `请求3`、`测试ddd`、`Health probe 副本`、`ww`。

## 根因

同一件事存在两套互相矛盾的口径：

| 位置 | 口径 |
| --- | --- |
| 删除侧 `endpoints.ts:endpointUsage`（P2-4.5 增补） | 请求节点的 `endpointId` 只是**来源标记**，节点自带请求快照，「删掉接口流程照跑」，不算引用、不拦、不清理 |
| 保存侧 `trigger.ts:endpointsBelong` | 每个请求节点的 endpoint 必须**在本项目存在**，否则整张流程拒绝保存 |

于是一删接口，引用它的流程就再也存不回去。另外两个事实让「流程照跑」这句话本身也不成立：

- `executions.endpoint_id` 对分区表是 `NOT NULL` + `ON DELETE CASCADE`（迁移 066），节点带着
  已删的 uuid 去插执行行会直接外键违约，执行即失败；
- 前端节点来源选择器把悬空 id 渲染成 `${method} ${节点名}` 的占位项
  （`FlowNodeDrawer.tsx:342`），看起来像还绑着，最容易漏改。

## 备选与取舍

- **A：放宽保存校验、`executions.endpoint_id` 改可空、删接口时把节点 `endpointId` 置空。**
  能兑现「删接口流程照跑」，但引入「无来源节点」这种新状态，接口维度历史/TopN 都得容忍
  NULL，且要改分区表所有分区的约束。用户在 2026-10-21 明确否决（担心长期管理混乱）。
- **B（采纳）：删接口时把流程请求节点当引用拦下。** 与手动套件成员同一纪律，数据模型不动，
  执行/统计口径不动。

## 修法

后端（`apitest-server/src/routes/endpoints.ts`）：

1. 新增 `ENDPOINT_NODE_REF_PATH` 与 `flowsUsingEndpoint()`：用 `$.**` 递归 JSONPath 扫
   `flows.nodes`，命中循环体内的请求节点，返回 `{ id, name, nodes[] }`（`$.**` 会同时命中
   循环体和其体内同一张卡，按名字去重后给人看）。
   JSONPath 的参数占位是**具名变量**：写成 `$2` 会被当成变量名解析并报
   `could not find jsonpath variable "2"`，必须 `jsonb_build_object('value', $3::text)`。
2. `endpointUsage()` 增加 `flows` / `flowNodeCount`，并把 `blocked` 扩成
   「手动套件成员 **或** 流程节点引用」。
3. `DELETE /endpoints/:endpointId`：即使 `?force=true`，只要 `usage.flows` 非空就返回
   409 `2003 "endpoint is referenced by flow nodes"`。force 表示「看过清单后接受连带删除」，
   但流程节点没有可自动完成的后续动作（改节点是内容决策），不能由确认框代劳。
4. `POST /endpoints/batch-delete`：被流程节点引用的接口与套件成员一样**跳过**并列进
   `blocked`（新增 `flowCount`），其余照删。

前端：

- `EndpointList.tsx` / `EndpointWorkspace.tsx`：`usage.flows` 非空时弹专用确认框，列出
  「流程 + 节点名」，只有一个按钮「去处理这些流程」，不给「仍然删除」。
- `api.ts`：`EndpointUsage` 增加 `flows`/`flowNodeCount`，批量删除结果的 `blocked` 行增加
  `flowCount`；`endpoints.batchDeletedPartial` 文案改成「被套件或流程节点引用」。
- i18n（中/英）新增 `endpoints.deleteFlowsBlockedTitle` / `deleteFlowsBlockedHint` /
  `usageFlow` / `goToFlows`。

## 保存与画布上的提示

拦得住新引用，还要让人看得见已经坏掉的节点（以及为什么「存下去了但跑不起来」）：

1. **保存报错点名节点**：`trigger.ts:endpointsBelong` 把差集里的节点名带进错误信息
   （`a node references an endpoint that does not exist in this project: "请求3", "测试ddd"`），
   前端 toast 直接显示这句（`FlowWorkspace.tsx` 的 `save` catch 本来就显示后端 message）。
2. **画布常驻徽记**：`StepNode` 在头部渲染 `TriangleAlert`，卡片左缘与底色换成保留的
   fail 色组（`.flow-node.is-dead-source`），悬停说明怎么修。判据是
   `knownEndpointIds`（进入编辑器时 `reloadEndpoints` 拉到的本项目接口全集），
   不是「清单里没找到」——清单是分页 store 态，缺一行不等于被删。
3. **列表模式同步**：`FlowStepList` 收 `deadSourceIds`，同一枚徽记 + 同样的行配色
   （`.flow-row.is-dead-source`）。列表是同一份文档的第二个投影，不能只有画布显示。
4. **保存成功后仍提醒**：保存本身会成功（后端把 `endpointId` 当来源标记），但执行这一步
   会撞 `executions.endpoint_id` 外键。所以有失效来源时把成功 toast 换成 warning
   `flows.savedWithDeadSource`，点名节点，避免「存下去就没事」的错觉。

## 存量数据

3 条流程的 8 个悬空节点**没有自动清理**（用户数据不动）。需要在界面上把这些节点的来源
改成现有接口，或删掉节点后重新保存；修好之后，B 方案保证不再产生新的悬空引用。
