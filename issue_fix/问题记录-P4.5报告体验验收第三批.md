## ① 报告的执行日志一直显示「正在加载」

**现象**

run 详情页报告 tab 里，点开一条用例后的「执行日志」块（以及步骤日志、截图）永远停在
「正在加载」；网络面板里 `/attachments?name=log` 一串 404，且同一名附件被反复请求。

**根因（两处叠加，都修）**

1. **附件引用的键错了（服务端）**。allure 结果 JSON 里一条附件引用是
   `{name, source, type}`：`name` 是展示名（`log` / `stdout`），`source` 才是报告包里的
   **实体文件名**（`<uuid>-attachment.txt`）。`lib/allureReport.ts` 的
   `normalizeAttachments` 只保留了 `name`，而附件路由 `readReportAttachment` 按包内
   basename 匹配——`?name=log` 在 zip 里没有同名实体，永远 404。
2. **在途响应被丢弃（前端）**。`AttachmentView` 的取数 effect 依赖 `loadAttachment`，
   而详情页与分享页都传**每次渲染新建的内联箭头函数**；effect 的 cleanup 把 `alive`
   置 false，父级任何一次重渲染（SSE 日志事件、run 轮询都触发）都会让在途请求的响应
   整个被丢弃，而 effect 守卫 `state !== "idle"` 又不再重发——状态从此停在
   `loading`。这正是「一直加载中」的直接来源：即使请求成功返回，UI 也收不到。

**修法**

- `allureReport.ts`：附件引用归一为 `{name, source, type}`（`ReportAttachment`），
  steps / cases / fixtures 的 `attachments` 全部换型；`view.attachments` 类型清单改按
  `source` 键归位（新增 `registerAttachmentTypes` 从 case/step/fixture 收集——
  pytest 适配器根本不产 `-attachment.json`，原清单恒为空，还连带让「报告包无附件」的
  提示误报）。`-attachment.json` 分支保留，键同样优先 `source`。
- 前端：`AttachmentView` 收整个附件引用，显示用 `name`、取数用 `source`；effect 去掉
  `alive` 旗子（迟到响应照常落地，React 18 对已卸载组件的 setState 是 no-op）；详情页
  与分享页的 `loadAttachment` 用 `useCallback` 固定身份。`api.ts` 配套
  `AllureReportAttachment` 类型。

**状态**：已修。旧报告包按需重解析（5 分钟缓存过期后），历史 run 的附件即恢复。

## ③ 报告失败数量对不上（实际失败 2，标题显示失败 1）

**现象**

最新 run（#15）：报告 tab 里失败状态的用例有 2 条（allure 包视图按 uid 展示），概要读数
与标题 chip 却显示「失败 1 / 跳过 15」。

**根因（两处）**

1. **唯一键把两条真实执行折叠成一行**。失败的两条是同名参数化用例（`@allure.title`
   是静态文案），两个 result 文件的 `name` / `fullName` / `historyId` 完全相同，唯一的
   身份差是文件 `uuid`。`pipeline_run_cases` 的唯一键
   `(pipeline_run_id, source, suite_name, case_name)` 不含它，`ON CONFLICT DO NOTHING`
   把第二条静默吞掉——表里只有 1 条 failed，计数（从表行重算）就是 1。
2. **`error` 状态被计进跳过**。`completePipelineRun` 的计数 SQL 是
   `failed = status='failed'`、`skipped = status IN ('skipped','error')`；而 Runner 把
   allure 的 `broken`/`unknown` 映射成 `error`，前端处处按失败色渲染（`caseRunStatus` /
   `matchesFilter` 的 `failed` 都收 `error`）——一条 failed + 一条 error 的 run，标题会
   显示「失败 1 / 跳过 1」。

**修法**

- 迁移 `044_p45_pipeline_run_cases_external_id.sql`：加 `external_id TEXT NOT NULL
  DEFAULT ''`（allure = 结果文件 uuid，junit = 空），唯一键加宽为
  `(pipeline_run_id, source, suite_name, case_name, external_id)`；旧约束按定义内容找
   再 DROP（038 的纪律）。
- Runner `report/allure.ts` 上报 `external_id`（结果 JSON 的 `uuid`，截 128）；
  `protocol.ts` 的 `ReportCase` 加可选字段（升级窗口里旧 Runner 报空串，退回旧去重
  口径，不会更糟）。
- `completePipelineRun`：INSERT 带 `external_id` 并对新唯一键 ON CONFLICT；计数改
  `failed = status IN ('failed','error')`、`skipped = status='skipped'`。
- `models/types.ts`：`PipelineRunCase.externalId` + mapper。

**验证依据（本机 dev 库，只读取证）**：#15 的报告包里两条
`projectIds 非法 UUID 被忽略且结果为空` 的 result 文件 `uuid` 不同、其余身份字段全同；
`pipeline_run_cases` 里只剩 1 条 failed——与折叠推断一致。

**状态**：已修。已折叠的旧 run 行不回填，重跑一次任务即恢复两行。

**复验补记（2026-09-03，用户复报「失败还是对不上」）**：run #16 仍显示失败 1——
**代码修对了，但跑的 Runner 没更新**：Runner 进程跑的是 `dist/`（构建产物，9 月 1 日
的），`external_id` 上报只在源码里；DB 取证 `pipeline_run_cases` 全部 36 行
`external_id=''`、而 #16 报告包里两条 failed 的 uuid 明明不同。修法即
`pnpm build` + 重启 Runner（已执行并确认注册）。**已入账的旧数据按报告包 uuid 手工回填**
（#12/14/15/16：插回被折叠的第二条 failed、把两条的 external_id 写成包内 uuid、从表行
重算 run 与 execution_index 计数——四条 run 均为 total 37 / failed 2，与报告包一致；
`case_total` 37 > 36 是因为 #13 之后任务命令加了一条用例的旧包不复核，37 是「包里 36 条
+ 被折叠补回 1 条」的表行数）。**教训**：跑 `dist` 的部署形状下，源码修复与生效之间隔着
一次 build——复验前先对账 `external_id` 是否真的在进库。

## ④ 产物大小都是 0 B

**现象**

run 详情页产物 tab 里所有产物的大小都显示 `0 B`，下载到的文件却是完整的。

**根因**

`routes/runners.ts` 的 fs 直传端点：路由里声明了 `let written = 0`，但真正数字节数的是
`TransformStreamCounter`（`guard`），`written` 从未被赋值；落库与响应都读了这个恒为 0
的局部量。磁盘文件由同一个 pipeline 写出所以是对的——只有 DB 错。

**修法**

删掉 `written`，UPDATE 与响应都读 `guard.bytesWritten`。

**状态**：已修。本机 dev 库的现存 artifacts 行已按磁盘文件大小一次性回填
（`size_bytes` 33KB–51KB，11 行），代码不含迁移逻辑。

## ⑥ 上报 commit 没变，为什么每次都入库？（复核 → 2026-09-03 用户改口径，已按新口径实现）

**现象**

`ingest_runs`（上报记录）每次执行都多一行，同一个 commit `493d7b2e` 报了 8 次，
`ingest_records` 跟着存了 8 份（186 行记录 vs 一份 27 行的快照）。

**原口径（v1 时的设计）**

`/ingest` 的幂等键是 `(repository_id, commit_sha, ci_run_id)`，CI 任务每条 run 注入的
`APITRACK_CI_RUN_ID` 就是 job id——每次执行都是一次新的 CI run，键必然不同。键里的
commit 只去重「同一次 CI run 的重投/重试」。当时理由：两次执行的结果可能不同
（修完重跑），合并会丢掉第二次的结论。

**用户改口径（2026-09-03）**

不期望同一 commit 每次都入库——后面数据会肿胀（实测已翻 8 倍）。仓库用例的「快照」
语义以 commit 为单位：同 commit 的重复执行不改变快照内容，只该更新「最近一次什么时候
跑的、结果是什么」。

**修法（迁移 045 + `lib/ingest.ts` + `lib/pipelineRun.ts`）**

- 键折形：插入侧把 `ci_run_id` 统一按 `''` 参与（冲突谓词 `(repo, commit, '')`），
  同一 commit 的任意上报（不管来自哪次执行）都命中同一行；列上保留真值
  （`COALESCE(NULLIF($15,''), …)` 回写「最近一次上报的 CI 来源」）。
- 新列 `ci_execution_count`：run id 变了才 +1（同一执行的重试/重投不推；SDK 直跑
  恒 '' 不推）——「跑过几次」数执行不数调用。
- `pipeline_runs.ingest_run_id` 的反查从 `ci_run_id = run.id` 改为
  `(project, commit_sha)`——折行后同一 ingest 行被同 commit 的多条 run 共享，
  `markCaseFilterNotRun` 的 `last_ingest_run_id` 判据语义不变（所有上报推同一行）。
- 迁移就地合并旧行：留最早那行（diff 定局的那次），`execution_index` 行改指保留行
  （先删同组多余 index 行防撞 `UNIQUE(kind, detail_id)`），`repo_test_cases.last_ingest_run_id`
  与 `repo_case_endpoints` 的 run 引用折到保留行，其余行删除——`ingest_records` 的
  CASCADE 把翻倍的记录收回来（350 行 → 69 行）。
- 前端 `IngestRuns.tsx`：原来显示 `ciRunId` 的位置改为「执行 N 次」
  （`repoCases.ciExecutionCount`），同 commit 折行后这行不随执行新增，「跑了 8 次都折
  在这」要能一眼读出。

**数据修正（本机 dev 库，一次性）**：16 行 `ingest_runs` 折成 4 行（按 commit），
保留行的计数按最新一轮快照回填（case_total 33 / failed 1 / request 9 / unmatched 5），
`ci_execution_count` 按各组实际执行次数回填（8760 组 1 次本地、737a3 组 3 次、
a0dd6 组 3 次、493d 组 8 次），`execution_index(kind='ingest')` 同步。

**状态**：已修。下次同一 commit 的 CI 执行：`ingest_runs` 不再新增行，`ci_execution_count` +1。
