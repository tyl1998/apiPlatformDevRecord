# P8-1 口径收口：三处通过率分叉 + 趋势汇总自指样本污染

> P8（数据统计）第一批，纯重构（开发内容见 `DEVELOPMENT_PLAN_P6-P10.md` 十二章
> 边界 1/2）。三个既有缺陷随本批收口——缺陷记本文件，计划文档只记范围与实现状态。

## ① 通过率三处口径分叉（缺陷）

**现象**：同一次套件执行，报告列表（`reports.ts` UNION 两侧）显示
passed/(passed+failed)（2026-09-03 用户改口径，skipped 不进分母），但：

- **报告详情与分享页**（`lib/reportPayload.ts` 的 `derivedColumns`）仍用
  `success/total`——skipped 进分母。25 过 / 15 skip 时列表显示 100%、详情显示
  62.5%，分享出去的外部链接与站内列表对不上。
- **套件结果通知模版**（`lib/alerts.ts` 的 `notifySuiteResult`）分母是
  `success + failed + skipped`——第三种算法。通知里读到的通过率与报告页对不上。

**根因**：2026-09-03 的口径改造（`issue_fix/问题记录-P4.5验收20260903第二批.md`
②）只改了报告列表与 run 详情页两处落点，`reportPayload.ts`（报告详情拼装，
列表/详情/分享三个消费方共用）与 `alerts.ts`（通知模版）漏改——改口径时不存在
单一事实源，散在各处的公式逐处对齐必然漏。

**修法**：

- 新建 `lib/metrics.ts` 口径库（P8 边界 2）：`PASS_RATE_SQL(prefix)` SQL 片段
  常量（嵌进 SELECT 列表，表别名由调用方传）+ `passRateOf(passed, failed)` TS
  侧同款（通知等 Node 内计算用，事件计数在手不查库）。SQL 与 TS 各持一份是
  刻意的：SQL 片段进 SELECT（聚合行一次算好），TS 供事件场景；分母语义必须
  一致——不含 skipped/canceled，null = 没有结论（不是 0%）。
- `reportPayload.ts` 的 `derivedColumns` 换 `PASS_RATE_SQL("se")`。
- `alerts.ts` 的 `notifySuiteResult` 换 `passRateOf(event.successCount,
  event.failedCount)`（原先的 `settled` 含 skipped）。
- `reports.ts` 报告列表 UNION 两侧手写的同公式 CASE 也收敛到 `PASS_RATE_SQL`
  （runner 侧列名不同——`passed_count`，replace 收编），防止两处再漂移。
- 趋势桶（trend）与汇总（summary）的 `passRate` 一并换 `passRateOf`：趋势桶
  语义上已等价（status 过滤挡掉非定局行，total == success+failed），换同一处
  实现是防漂移；summary 原本就对。

**状态**：已修。全跳过的套件报告在详情/分享页从 0% 变为 null（「没有结论」），
与列表一致；通知读数与报告页一致。

## ② 单步调试自指索引行污染趋势样本（缺陷）

**现象**：流程编辑器里单步调试一个脚本/条件/等待/数据库节点后，趋势页的失败率
读数变化——「调试了一下某个节点」混进了趋势与汇总的父执行样本，而同一份样本在
统一执行记录列表里根本看不到（列表早就排除了）。

**根因**：非 HTTP 单步调试写的是一次性自指父索引（`routes/flows.ts` 的
`executeGenericStep`，`detail_id = id`，kind='flow'）。统一执行记录列表侧
（`executionIndex.ts:23`）一直有 `detail_id <> id` 排除；趋势（trend 的 LEFT
JOIN ON 条件）与汇总（summary 的 WHERE）漏了同一个过滤——一处口径三处写，
列表改了趋势汇总没跟上。

**修法**：`metrics.ts` 导出 `NOT_SELF_DEBUG = "detail_id <> id"`（注释说明自指
是这类行唯一稳定标记：两张表 id 都是 randomUUID，真实父执行不可能撞上）；
trend 的 ON 条件与 summary 的 WHERE 各补 `AND ei.detail_id <> ei.id` / 
`AND detail_id <> id`（片段嵌进各自 SQL）。

**状态**：已修。趋势/汇总读数与列表可见样本对齐。

## ③ includeRepo 只作用于 summary 第一段（缺陷，本批不动，记录判定）

**现象**：趋势/汇总页打开「含仓库执行」开关后，总量读数（第一段，读
`execution_index`）变化，失败分布两段（byEndpoint / byType，读叶子 `executions`）
纹丝不动。

**根因**：不是漏改 SQL——byEndpoint/byType 读叶子 `executions` 表，而 ingest
上报与 runner 执行的失败**不落在那张表里**（ingest 记录在 `ingest_run_records`、
runner 用例在 `pipeline_run_cases`）。数据源错位，SQL 加过滤也变不出来。

**判定**：P8 边界 1 既定安排——「`includeRepo` 的一致性在新归因统计上直接做对
（旧 summary 的②③段随新页替换退役）」。本批（P8-1）不动②③段；P8-4 的
`/stats/*` 新接口从正确的数据源聚合。已在 `reports.ts` summary 的注释里写明
这笔账，防止后来人当漏改去「修」。

**状态**：判定为数据源错位非 SQL 漏改，按计划留给 P8-4 新接口收口。

## ④ 趋势页加载失败：summary 拼进箭头函数源码（P8-1 自伤缺陷，用户实测发现）

**现象**：P8-1 改动重启后，趋势页整体报「趋势加载失败」；`.dev-logs/api.log` 里
`GET /reports/summary` 500（`syntax error at or near "=>"`，42601，位置 530），
`/reports/trend` 本身 200——趋势页把两个请求 `Promise.all` 绑在一起，summary
挂了整页都算失败。

**根因**：`metrics.ts` 的 `NOT_SELF_DEBUG` 从字符串常量改成箭头函数（为给趋势的
JOIN 加表别名前缀）时，summary 的 SQL 模板里仍写 `${NOT_SELF_DEBUG}`（没调用）——
模板插值把函数源码文本拼进 SQL，Postgres 扫到 `=>` 即语法错误。trend 侧写的是
`NOT_SELF_DEBUG("ei")` 所以没炸。`tsc` 抓不住这类问题（模板里插任何值都合法），
`pnpm check` 通过不代表 SQL 可跑。

**修法**：summary 侧补调用括号 `${NOT_SELF_DEBUG()}`；tsx 直跑片段工厂验证四种
调用形态（`NOT_SELF_DEBUG("ei")` / `NOT_SELF_DEBUG()` / `PASS_RATE_SQL("se")` /
`PASS_RATE_SQL("pr", "passed_count")`）产出全部为合法 SQL 文本。

**状态**：已修（`tsx watch` 自动重载生效，未登录请求该路由回 401 而非 500）。
