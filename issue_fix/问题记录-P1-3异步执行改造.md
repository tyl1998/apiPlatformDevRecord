## 问题 1：SSE 流被浏览器拦截，执行「慢 3 秒」

**现象**：接入异步执行后，单发调试体感明显变慢（约 3 秒才出结果），但后端日志显示
入队→执行→完成仅 50~70ms。

**根因**：`reply.hijack()` 接管原始响应后，Fastify 不再走正常发送流程，`@fastify/cors`
在 onRequest 挂到 reply 上的 `Access-Control-*` 头**不会写出**。浏览器直接拦掉这条
跨域 SSE 流，前端 `fetch` 抛错后进入重连退避，等待中的执行只能靠 3 秒轮询兜底完成。

关键迷惑点：**curl 测不出这个问题**——curl 不检查 CORS。所以排查时 curl 一切正常，
只有浏览器慢。

**修法**（`routes/stream.ts`）：hijack 后手动把 CORS 头搬进 `writeHead`。只搬
`access-control-*` 与 `vary`，不整包 spread——其余头是给 JSON 响应准备的，套到
event-stream 上只会带来意外。

**状态**：已修复（POST→终态事件 50~67ms）

## 问题 2：响应面板闪屏

**现象**：响应很快（~50ms）时，响应区出现「结果 → 空白 → 结果」的闪烁。

**根因**：把运行状态做成了**替换**结果面板——`if (running || pending) return <等待面板>`，
结果区先清空显示「排队中」，完成后再整块填回。

**修法**（`EndpointWorkspace.tsx` ResponsePanel）：
- 运行状态只占标题栏（排队中/执行中 + 取消按钮），结果 body **保持挂载**不动
- 保留的旧响应用 `opacity: .5` 置灰，避免被误认成正在等的结果
- 切页签的时机从「点发送时」挪到「结果到达时」，否则会在旧 body 上跳页签

**状态**：已修复

## 问题 3：刷新后执行器面板消失

**现象**：登录后能看到系统设置 → 执行器；刷新页面后整块消失。

**根因**：`authStore.hydrate()` **定义了但从未被调用**。刷新后 `token` 从
localStorage 恢复（能过路由守卫），但 `user` 恒为 `null`，`user?.isSystemAdmin`
恒为 `false`——按权限门控「整块不渲染」的 UI 静默消失，没有任何报错。

**修法**（`main.tsx`）：`Root` 里 `useEffect(() => void hydrate())`。

**状态**：已修复

## 问题 4：修复问题 3 时漏 import useEffect，整页白屏

**现象**：补上 `hydrate()` 调用后，整个应用白屏。

**根因**：`main.tsx` 只 import 了 `createRoot`，`useEffect` 是 undefined，
组件渲染直接抛 ReferenceError。

**教训**：改完代码必须跑 `tsc --noEmit` 再交付。Vite 热更新只反映运行时，类型错误
（尤其是漏 import）在浏览器里表现为整页白屏而不是编译报错。此前让用户直接硬刷新
验证是错误做法——工具链的检查门槛被我跳过了。

**状态**：已修复（补 import + `tsc --noEmit` 通过）

## 问题 5：运行记录 pageSize 切换无效

**现象**：接口编辑页侧栏「运行记录」的每页条数看似可切，实际列表行数不变。

**根因**：两个叠加问题：
1. `EndpointWorkspace.tsx` 请求里 `pageSize` 写死为 `20`
2. 分页用的是 antd `Pagination` 的 `simple` 模式——**该模式根本不渲染每页条数
   选择器**，所以界面上根本没有可切的控件

**修法**：新建共用组件 `SidebarPager`（运行记录与用例列表共用），显式提供
pageSize 选择 + simple 页码步进。

**状态**：已修复

## 问题 6：列表出现两个 pageSize 选择器

**现象**：只有「Health probe 副本」这一个接口出现两个每页条数下拉框，其他接口正常。

**根因**：rc-pagination 的 `showSizeChanger` **默认值不是 false，而是 `total > 50`**
（`Pagination.js: showSizeChanger = prop === void 0 ? total > totalBoundaryShowSizeChanger : prop`）。
我手写的 Select 之外，antd 在总数跨过 50 行时又自动渲染了一个。只有记录超过 50 条
的接口会暴露——所以现象是「特定接口」而不是「全局」。

我最初的注释断言「simple 模式不渲染 size changer」是错的，`simple` 只影响页码样式。

**修法**（`SidebarPager.tsx`）：删掉手写 Select，改用组件自带 `showSizeChanger`，
并**显式传参**——传参的同时也挡住了那个隐式的 50 条阈值，控件不会凭空出现。

**状态**：已修复

## 问题 7：用例列表没有分页

**现象**：用例列表一次渲染全部，无分页、无每页条数选项。

**根因**：后端 `GET /endpoints/:endpointId/cases` 不分页；前端也无分页器。

**修法**：**前端分页**（`CaseBox.tsx`）。刻意不做服务端分页，原因：
- 筛选（关键字/状态/标签）是全量客户端过滤，改服务端分页会让筛选退化成
  「只筛当前页」——正确性回退
- 状态筛选依赖 `lastRun`，由 `latestRuns` 在应用层拼装，推回 SQL 要重构
- 一个接口的用例量有界，全量加载只有 2 次查询

**状态**：已修复

## 问题 8：死 worker 记录堆积

**现象**：反复重启后，执行器面板堆满「离线」worker 行，需要 1 小时后才清掉。

**根因**：优雅停机会自己摘注册，但被 SIGKILL 时来不及——`tsx watch` 每次保存文件
都换一个 pid，开发时保存几十次就堆几十行死记录。

**修法**（`worker.ts`）：启动时用 `process.kill(pid, 0)` 检查**本机**历史行的进程
是否还在，仅 `ESRCH`（进程不存在）时删除。`EPERM` 不删——那说明进程活着，只是
属主不同。只查本机，因为 pid 只在同机有意义。跨主机陈旧行仍由回收扫描按 1 小时清。

**状态**：已修复

## 问题 9：多 worker 时回收扫描重复执行

**现象**：N 个 worker 各挂一个回收定时器，同一批次被并发重算并各自广播一次进度。

**根因**：`reapStale()` 的 UPDATE 本身幂等，但紧随其后的 `settleBatch` 会被重复
触发——这是真 bug，不是「冗余扫描」那么简单：前端会收到同一批次的多份事件。

**修法**（`worker.ts`）：`pg_try_advisory_xact_lock(8013301)` 事务级互斥，抢不到就
跳过本轮。选事务级而非会话级，是因为它随事务结束自动释放——进程崩了锁不会留下，
不需要超时/续租。`settleBatch` 移到 COMMIT 之后，保证读到已落定的行。

**状态**：已修复

## 问题 10：多 worker 会重复发请求吗？（验证结论）

**疑问**：多个 worker 抢同一队列，一次入队会不会发出多个请求。

**结论**：不会，**at-most-once**，两层保证：
1. BullMQ 原子出队——但这是 at-least-once，worker 锁续期失败会重投 job，仅靠这层不够
2. `performRun` 认领带 `WHERE status = 'queued'`，被重投的 job 匹配不到行，在
   `fetch` 之前就返回 false

**实测**：三 worker 抢同一队列，80 次入队，靶子服务恰好收到 80 个请求，零重复。

**取舍**：工具会向真实服务发 POST/DELETE，「执行丢了」可重跑，「静默发了两次」无法
挽回，所以选择 at-most-once 而非 at-least-once。

**状态**：已确认（非 bug）

## 问题 11：断言在哪里执行？（架构澄清）

**疑问**：用例校验是在 worker 里做，还是 worker 发完请求后平台再校验。

**结论**：**在 worker 内**（`lib/run.ts`）。发请求 → 读响应 → 断言求值 → 判定 status
→ 同一条 `UPDATE` 落库，一次写入定终态。

- 有断言时断言说了算，没断言才看 HTTP 状态码
- 若改成平台校验，会出现「终态已落、断言未判」的窗口期，需要二次写入翻转 status，
  而 status 驱动仪表盘/最近结果/批次汇总，多一次翻转就多一处不一致
- 断言跑在**截断后**的响应体上（10KB），保证「断言通过」能从 UI 文本复现

**状态**：已确认（架构决策）

## 问题 12：start.sh 被自动化工具超时杀掉

**现象**：通过 bash 工具运行 `./start.sh` 后命令 120s 超时，且后台子进程一并被杀。

**根因**：`nohup` 只忽略 SIGHUP，不会脱离**进程组**。自动化工具等待命令的整个进程组
退出，后台服务一直挂着导致超时，超时后连进程组一起 SIGKILL。

**修法**：非脚本缺陷。改用 `background_process` 工具运行 `./start.sh`（它不等待后台
子进程），或用户在真实终端里运行（终端不等待后台任务，立即回到提示符）。

**状态**：环境问题，脚本本身可用

## 问题 13：`--restart` 不带服务名时脚本崩溃

**现象**：`./start.sh --restart` 报 `RESTART_SERVICES[@]: unbound variable`。

**根因**：macOS 自带 **bash 3.2**，空数组在 `set -u` 下展开 `${arr[@]}` 直接报错
（bash 4.4 才修复此行为）。

**修法**（`start.sh`）：按数组长度分支——有服务名走有参调用，否则走无参调用，
不展开空数组。

**状态**：已修复

## 问题 14：DEVELOPMENT_PLAN.md 第二轮编辑被还原

**现象**：应用完 P1-1 断言收尾的文档改动后，文件被还原成两轮编辑之间的状态——第一轮
（P1-3 收尾）还在，第二轮的批次表/4.0.1/4.0.2/依赖表全部丢失。

**根因**：不明（文件不在 git 里，无法从版本历史确认）。疑似编辑器 buffer 或外部同步
覆盖。

**修法**：按当前文件内容重新应用全部改动并逐条验证（`rg` 确认关键词、行数从 759

**经验**：**重要文档建议纳入 git**——这类文件一旦被还原，没有版本历史就只能在
「两轮之间」的状态上重新打补丁，靠记忆重建改动。

**状态**：已修复（重新应用）

## 经验总结

1. **CORS 类问题 curl 永远测不出来**。涉及浏览器跨域（SSE、fetch）的故障，必须用
   带 Origin 的请求或浏览器 Network 面板验证，`curl` 全绿不代表浏览器能过。
2. **antd/rc-* 的默认值别靠记忆**。`showSizeChanger` 默认 `total > 50`、`simple`
   仍渲染 size changer——这类默认值会随数据量变化改变行为，显式传参是唯一安全写法。
3. **门控 UI 用「整块不渲染」时，权限数据的初始化失败 = 功能静默消失**。
   `hydrate()` 没被调用、刷新后管理员面板消失这种 bug，比显式报错难定位一个量级。
4. **改完代码必须过 `tsc --noEmit`**。漏 import 这类错误热更新不报、浏览器白屏，
   工具链检查门槛不能被跳过。
5. **跨进程状态（SSE 事件、并发回收）要防「幂等之外的重复副作用」**。回收扫描的
   UPDATE 幂等不等于安全，后面的广播/重算会被 N 个进程各做一遍——事务级 advisory
   lock 是低成本解法。
6. **macOS bash 3.2 的 `set -u` + 空数组展开会崩**，兼容写法是长度分支或
   `${arr[@]+...}`。
7. **快速失败优于降级**。Redis/worker 不可用时直接报「执行队列不可用」而不是内联
   执行，避免同一份代码出现两条执行路径（并发/取消/进度行为不一致，排查只能靠猜）。
8. **异步化的用户可见收益要用「变快」体现**：SSE 推流后单发执行 50ms 级返回，但
   一旦流坏了退回轮询兜底，用户感知是「慢」而不是「坏了」——兜底延迟要尽量短。
