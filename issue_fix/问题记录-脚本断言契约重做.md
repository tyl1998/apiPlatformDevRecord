# 脚本断言契约重做（ctx.assert 取代 return）— 问题记录

> 记录 4.0.2.5 / 4.0.2.6 脚本断言契约重做期间发现的问题、根因与修法。
> 契约本身的设计取舍见 `DEVELOPMENT_PLAN.md` 4.0.2.5 / 4.0.2.6，此处只收录问题。

---

## 一、契约重做本身（1 项，设计问题）

### #1 旧契约要求 `return` 真值，一条脚本只能表达一个判断

**现象**：断言脚本必须 `return` 真值才算通过；多条检查得自己 `&&` 起来，失败了
也说不出是哪一条。用户期望在脚本内直接 `assert`。

**修法**（用户确认三条规则）：
1. `ctx.assert(...)` 决定结果，失败即 `throw`，走沙箱既有的错误通道。
2. 无断言且无报错 = 通过（用户明确否决「必须 return 或必须 assert」）。
3. `return` 只是证据：记录进 `AssertionResult.actual`，不参与判定。

**状态**：已修复（4.0.2.5）

## 二、验收反馈（3 项，UI 问题）

### #2 执行用例后同一份脚本结果展示两次

**现象**：脚本断言行内渲染运行结果的 check 列表（`ScriptChecks`），而响应面板/
执行快照的 `AssertionResults` 又渲染一遍；用户再点一次试运行，编辑行、试运行面板、
响应面板三处出现同一份 ✓/✗。

**根因**：编辑行把「运行结果明细」和「试运行面板」都塞进了同一个编辑器区块，各自
独立渲染，没有归属约定。

**修法**：编辑行只留通过/失败标记；check 明细只归「响应面板/执行快照（只读
`AssertionResults`）」和「试运行面板」两个地方。明细不再在行内重复。

**状态**：已修复

---

### #3 失败时 message 与 ✗ 行重复

**现象**：soft 模式失败同时输出 `✗ equal 400 — expected 400, got 200` 和
`1 of 3 checks failed: expected 400, got 200`，同一信息两遍，用户反馈「太啰嗦」。

**根因**：`runScriptAssertion` 对 `failedChecks > 0` 生成了一条「N of M checks
failed: …」汇总，而每条失败又单独记录在 `checks` 里。

**修法**：断言失败（hard 或 soft）**不再生成汇总 message**——`checks` 明细是唯一
信息源。沙箱加 `assertThrew` 标志区分「断言抛的错」与「脚本自己抛的错」：前者
不产 message，后者（TypeError、超时）照常带，因为没有哪条 check 能解释它。

**状态**：已修复

---

### #4 试运行后执行用例，脚本编辑器仍挂旧试运行结果

**现象**：先点试运行（脚本是 A 版），再执行用例（脚本已改或未改），试运行面板
仍显示 A 版的旧结果，看起来像用例没跑。

**根因**：试运行结果存在 `ScriptAssertionEditor` 内部 state，脚本内容变更或新执行
结果落地都不会清空。

**修法**：试运行结果在**内容变更**或**`resetSignal` 变更**（编辑器的 `results`
指向新的执行结果）时清空。

**状态**：已修复

## 三、命名与展示整理（4.0.2.6）

### #5 多个脚本断言无法区分

**现象**：一个用例挂多个脚本断言，编辑器都叫「私有」，执行结果都叫「自定义脚本」，
只能靠展开看内容猜。

**修法**：`Assertion` 增加可选本地 `name`（存在 jsonb，无迁移；对齐
`HookConfig.name` 的引用级标签语义）。编辑器脚本行加名字输入框，留空回退「脚本 N」，
执行结果用它当标签。

**状态**：已实现

### #6 return 上下文把结果行撑爆

**现象**：`return` 值最长 4KB，内联成一行 span，长 JSON 直接打乱整行，与 ✓/✗ 混在
一起。

**修法**：`return` 值改独立折叠块：≤120 字符直接显示，更长折叠成单行 + 「展开/收起」，
展开后等宽块内可滚动。试运行面板同一套样式。

**状态**：已实现
