# 容器档取消不杀容器（要等任务跑完才落 canceled）

- 日期：2026-09-03
- 模块：apitest-runner（`src/executor.ts` / `src/executor/container/`）

## 现象

容器档（`sandboxMode=container`）任务启动后点取消：平台侧状态立刻变 `cancelling`，但容器照常跑，脚本自然跑完之后 run 才落 `canceled`——「取消要在任务完成后才生效」。进程档取消是即时的（SIGTERM 进程组，5s 后 SIGKILL），clone 阶段取消也正常。

## 根因

取消链路本身没断——「取消只经心跳下发」（约定 6）工作正常：平台 `POST /runner/jobs/:jobId/heartbeat` 在 `cancelling` 时正确回 `cancel:true`（`routes/runners.ts`），Runner 的 `onCancel` 也收到了并置了 `cancelRequested`。断点在 executor 的执行段：

- `executor.ts` 的 `onCancel`/`onLost` 只杀 `currentHandle`，而 `currentHandle` 只在 `spawnFn`（clone 阶段、进程档脚本）里赋值；
- 容器档脚本走 `containerRuntime.run()`，**不经过 spawnFn** → 整个脚本阶段 `currentHandle` 恒为 null，`currentHandle?.kill("cancel")` 是空操作；
- 两条容器通道（cli / api）各自有完整的杀梯子（`docker stop -t 5` → `docker kill`，10s escalator），但只挂在内部 `timeoutTimer` 与 `registerInflightKill`（Runner 停机用）上，没接到每 job 的取消路径；
- 于是容器一路跑到自然退出，executor 这才因 `cancelRequested=true` 把终态报成 `canceled`。

## 修法

把通道的杀梯子交回 executor，取消路径直达容器：

1. `ContainerRunOpts` 新增 `onReady?: (kill) => void`（`container/runtime.ts`）；
2. cli 通道在 spawn 后、api 通道在 `containerId` 赋值后调用 `opts.onReady?.(kill)`；
3. `executor.ts` 增加 `containerKill`，`onCancel`/`onLost` 同时杀 `currentHandle` 与 `containerKill`；`onReady` 交接时若取消/丢租约已先到（镜像拉取、storage-opt 重试窗口、cli 的 runOnce 重入），到手立即补杀，否则那次取消永远停在「已请求、没人执行」；
4. cli 通道的 escalator 从单发 `setTimeout` 改为重复 `setInterval`（每 10s 一发 `docker kill`，run 结束清掉）：取消落在镜像拉取窗口时容器尚未创建，第一轮 stop/kill 会扑空（`No such container`），单发 escalator 同样扑空的话这次取消就再也没人执行了；已在杀则不重复起 interval（防取消+超时先后各调一次 kill 泄漏句柄）。对已死容器多发 kill 只是无害报错。

修后取消时序：点取消（状态 `cancelling`）→ 下一拍心跳（≤30s，阶段推进会 poke 提前）带回 `cancel:true` → 杀梯子 `docker stop -t 5`（容器内 PID1 收 TERM，5s 后 daemon 自己 SIGKILL，后台进程一锅端）→ `docker run` CLI 退出 → Runner 报 `canceled`。**30 秒以内的信号下发延迟是「取消只经心跳下发」的既定设计**（心跳间隔由平台下发，`RUNNER_HEARTBEAT_INTERVAL_SECONDS=30`），不属于本缺陷；要更快的下发需要改协议（独立推送通道），未动。
