# 问题记录 — P4.5 容器档 SDK 回连不通与缓存引导

日期：2026-09-04 · 阶段：P4.5 容器档（qas 任务本地验证）· 关联：`问题记录-P4.5S3产物直传三缺陷与env密钥漂移.md`

## 缺陷一：容器档 SDK 上报 Connection refused

### 现象

- qas 任务（container 档）case 全过，但 `ingest_runs` 无新行；
- pytest warning：`apitrack could not report this run to http://localhost:3000/ingest
  (URLError: Connection refused)`。

### 根因

`APITRACK_URL` 由 claim 时 Runner 拨号的 Host 头推导（本机部署 = `localhost:3000`）。
进程档 Runner 在宿主上、localhost 可达；**容器档的 SDK 在沙箱容器里**，`localhost`
指向容器自身。第一版修法（改写为 `host.docker.internal`）不可移植：该名字只在
Docker 系桌面产品内置，Linux 原生 docker 不存在。第二版修法（自查 job 网桥网关 IP
做 `--add-host`）在 Mac 上证伪：docker 网桥在 Linux VM 里，查出的网关是 VM 地址、
不是 macOS 宿主（宿主自连网关也 refused）。

### 修法（最终版）

- `jobSpec.ts` 的 `containerLoopback`：container 档的 `APITRACK_URL` 回环地址改写为
  `host.apitrack.internal`（平台自己的命名空间）；进程档不动；显式配 `PUBLIC_BASE_URL`
  时不改写（那已是全局可达地址，平台不猜）。
- Runner `ContainerSpec.extraHosts: ["host.apitrack.internal:host-gateway"]`——
  `host-gateway` 是 docker 20.10+ 官方 token，daemon 替换为「容器到宿主的网关」：
  桌面产品是宿主转发地址、Linux 原生是网桥网关，两种环境同一个值，零网络拓扑假设。
  cli 通道翻译为 `--add-host`，api 通道翻译为 `HostConfig.ExtraHosts`。
- 实测：容器内解析 `host.apitrack.internal` → 宿主转发地址，`/health` 200，
  上报落库（commit `574c01e`）。

### 伴生缺陷（ingest FK 23503）

`/ingest` 重投时 500：`execution_index` 的幂等键仍是 `(kind, detail_id)`，而
ingest_runs 已折形为 `(repository, commit)`；折行 `execution_index_id` 为 NULL 时
重投，ON CONFLICT 走 UPDATE、本次新签的 indexId 没插进去，回填却写它 → 外键失败。
修法：INSERT 加 `RETURNING id`，回填与返回值统一用真实行 id（`effectiveIndexId`）。
存量 5 行 NULL 已回填。

## 缺陷二：容器档缓存「配置了但没缓存上」

### 现象

qas 任务配置 `cache_paths={.venv,.cache/pip}`、`cache_key_files={requirements.txt}`，
日志 `linked 2 path(s), 0 warm`，但宿主缓存目录 `~/.apitrack-runner/cache/.../.venv`
为空（0B）；第二次运行仍然全新 pip install。

### 根因（两层）

1. **脚本形状**：steps 写的是裸 `pip install -r requirements.txt`——装进容器系统
   Python（`/usr/local/lib/python3.10/site-packages`），容器删除即消失；挂卷挂在
   `/workspace/.venv` 与 `/workspace/.cache/pip`，从头到尾没被写过。缓存机制本身
   工作正常（key 稳定、挂载成功），缺的是「把依赖装进缓存路径」这一步。
2. **易用性缺口**：要求用户写 `/workspace/.venv` 这类容器档专属路径不合理——
   「别人不会写」。

### 修法

- **下载缓存自动引导**（Runner `buildScriptEnv`）：容器档 + 任务配了缓存时注入
  `PIP_CACHE_DIR=/workspace/.cache/pip`、`UV_CACHE_DIR=/workspace/.cache/uv`
  （`??=`，任务 env 优先）。裸 `pip install` 的脚本零改动即获得「第一次下载的包
  留在执行机器上」。刻意**不**做 `PIP_PREFIX`/`PYTHONPATH` 安装重定向：钉死
  python 版本路径、隐式改写 pip 行为，换镜像即坏且难排查。
- **完整 venv 缓存靠表单引导**（i18n `cacheHint`）：提示列 `.venv` 进路径 + 命令里
  建 venv（`python -m venv .venv && .venv/bin/pip install ...`），装好的 venv 下次
  直接复用。进阶需求显式写，不隐式猜。
- 实测：第二次运行 `2 warm`（pip 下载缓存命中）+ `Using cached ...`。

## 附：Runner 重启时序的 90 秒空窗（非缺陷，记录备查）

重启 Runner 时恰有 run 刚被旧进程认领、尚未落 job 目录即被 kill：新进程无从恢复、
心跳停止 → 租约 90 秒到期 → scheduler 判 `aborted`。设计如此（进程档恢复依赖
job 目录的 state.json/exit_code，认领后未落盘的窗口只能靠租约回收）。运维含义：
重启 Runner 前先等在途 run 落终态，或接受可能一条 run 变 aborted。

缓存第二次运行命中）。
