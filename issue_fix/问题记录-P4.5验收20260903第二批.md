## ① 用例树没有绑定到最新一次运行的报告（缺陷）

**现象**：run 23（c1f4d1ba）上报与报告解析都成功，用例树的「绑定任务 / 最近报告」列
仍然全部「—」。

**根因**：allure-pytest 的 `fullName` 不是 pytest nodeid——它把 `test_case/auth/test_auth.py::test_x`
归一成 `test_case.auth.test_auth#test_x`（路径分隔变点、`::` 变 `#`）。迁移 047 与
`ingest.ts` 的 `LATEST_REPORT_LATERAL` 按「guessed_case_key 去参数化后缀 == SDK case_key」
匹配，两边形态不同，LATERAL 一条都匹配不上。047 注释里「allure 的 guessed_case_key
就是 nodeid」的假设只对原始 nodeid 成立，对适配器归一后的 fullName 不成立。

**修法（两侧，不回写历史数据）**：
- Runner 侧 `report/allure.ts` 新增 `normalizeFullName`：带 `#` 的 fullName（allure-pytest
  产物形态）逆变换回 nodeid 形态（`#`→`::`、包段点号→`/` 并补 `.py`），参数化后缀
  原样保留（服务端 regexp_replace 剥）。不带 `#` 的（name 兜底 / junit / 其它语言适配器）
  原样透传，不猜。新上报从此存 nodeid 形态，直接命中 047 的表达式索引。
- 服务端 `LATEST_REPORT_LATERAL` 加第二个匹配分支救**历史行**（修复前落的点号形态）：
  `LIKE '%#%'` 门 + `concat(replace(split_part(k,'#',1),'.','/'),'.py::', regexp_replace(split_part(k,'#',2), …))`
  ——与 Runner 侧同一个逆变换，读时做，不回写。该分支不走 047 索引：它是救旧数据的
  过渡，新数据不再产生点号形态，成本随历史行消亡。
- 匹配键推导验证（tsx 直跑 parseAllureResult）：`test_case.auth.test_auth#test_a` →
  `test_case/auth/test_auth.py::test_a`；参数化与 name 兜底各形态正确。
- dev 库实测：兼容分支让 run 23 的 40 行全部挂上树（passed/skipped 判定正确）。

**注意**：junit 的 `classname::name` 本来就对不上（边界 13 best-effort 语义），不受影响。

**同根因的第二处（同日追修）**：单用例详情的**步骤树装载**（`ingest.ts` 的
`/repo-cases/:caseId`，`latestReport.steps`）拿报告包里的 `fullName`（点号形态）直接比
case_key——同样的形态错位，步骤树永远缺席，兜底文案被误读成「没有步骤」。修法同一把尺：
装载处 `fullNameToNodeid`（`#`→`::`、包段点号→`/` 补 `.py`，两边再去参数化后缀）后比对。
报告包是 zip 原文改不了，归一只能在读取侧做（Runner 侧 normalizeFullName 只管新上报的
guessed_case_key）。空态文案同步改写清楚：步骤 = `with allure.step(...)`，没有就是代码里
没写或 junit-only。dev 库实测：run 23 报告包 85 个结果文件中带步骤的（如
`test_login_success...` 的「发起登录请求 / 校验响应包络 code=0 / 校验返回 token 与用户
信息」）在修复后可挂上树。

**状态**：已修。历史 run 靠兼容分支当场可见；下次执行起走索引路径。

## ② 通过率口径：分母只算有结论的（用户改口径）

**现象**：run 25 过 / 15 skip 时，报告页通过率 25/40 = 62.5%——被跳过的用例没有给出
结论，算进「没通过」拉低了读数。

**改口径**：通过率 = passed / (passed + failed)，skipped 不进分母。**error（allure
broken/unknown）已经算失败**：Runner 把 broken/unknown 映射成 error、`completePipelineRun`
计数把 error 归入 `failed_count`（2026-09-02 第三批 ③ 已改）、树侧 `LATEST_REPORT_LATERAL`
的判定同样 `status IN ('failed','error')` 即失败——三层口径一致，本轮无需再动。

**落点三处**：
- `PipelineRunPage.tsx`：`passRate = passed / (passed + failed)`（分母 `judgedCount`）。
- `reports.ts` 报告列表 UNION 两侧（suite / runner）：`pass_rate` 分母从 `total` /
  `case_total` 改为 `success_count + failed_count`，守卫条件同步（全 skip 的报告现在读
  null——「没有结论」而不是 0%）。
- 趋势 / 汇总页（`reports/summary`、趋势桶）**本来就是** success/(success+failed) 口径
  （`settled` / status IN ('success','failed')），dashboard 的 `judgedCount` 同款——
  这轮只改了偏离口径的两处，其余对齐。

**状态**：已修。

## ③ 任务编辑页：未保存提示 + 快捷键保存（交互，对齐套件编辑）

**改法**（`CiTaskEditor.tsx`，照 `SuiteWorkspace` 的整套安排）：
- 载入后签一份表单快照（`snapshot`，canonical JSON），`dirty = 快照 ≠ 当前表单`；
- dirty 时标题旁显示 `chip-warn`「未保存 · ⌘S 保存」（`RepoPageHead` 的 `title` 放宽为
  `ReactNode`，其余四个调用方不受影响）；
- 注册 nav guard：侧栏/页内导航离开时弹「放弃未保存的修改？」确认；
- `Cmd/Ctrl+S` 保存（拦浏览器保存对话框，dirty 才触发）；
- 保存成功 / 「新建调度」的静默保存后 `setSnapshot(formCanonical())` 使 dirty 失效
  ——后者是原地路由切换，还要显式 `setGuard(null)`，不该再弹确认。
- 新建页以「表单有任何内容」为脏：没有快照基准时首次改动即脏（快照在 `load` 只对
  既有任务签，新建页的基准是空表单——`snapshot` 保持 undefined 时 dirty 恒 false 会让
  新建页永不提示，所以新建页首次渲染即签空表单快照）。

**状态**：已实现。
