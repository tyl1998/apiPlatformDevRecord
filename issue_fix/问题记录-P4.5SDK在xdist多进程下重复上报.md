# P4.5 SDK 在 xdist 多进程下重复上报、records 撞序号静默丢弃

## 现象

「纯测试」仓库加了 pytest-xdist（HEAD commit `add pytest-xdist plugin`，pytest 头部
`created: 4/4 workers`）后，一次 run 实际打了 **5 个 `POST /ingest`**（api.log：3+2 两拨，
1 个 controller + 4 个 worker 各自 `pytest_sessionfinish` 上报一次——`pytest11` entry
point 在每个 pytest 进程里都会自动加载插件）。合并进同一行 `ingest_runs` 后：

- `case_total = 0`、`is_full_inventory = t`，行上警告
  `is_full_inventory was set with an empty inventory; reconciliation was skipped`（最后
  一批的空 inventory 覆盖了前面 33 条的计数）；
- 36 个用例、多数在打平台 API 的 e2e，`ingest_records` 里只剩 **9 条**（seq 0–8，恰好是
  某一个进程那批）；其余 4 个进程的 records **全部静默丢失**。

## 根因

两个组件各按各自的设计正确工作，组合起来错位：

1. **SDK 无 xdist 感知**：每个进程独立探测「范围内有没有过滤」并各自决定
   `is_full_inventory=true`、各自从 `seq = 0` 给 records 编号（`collector.py` 的注释明确
   seq 是「批次内幂等键」——单进程假设）。
2. **平台的合并语义按协议正确**：`(repository_id, commit_sha, ci_run_id)` 幂等合并、
   records 靠 `UNIQUE (ingest_run_id, seq)` + `ON CONFLICT DO NOTHING` 去重（重投幂等，
   边界 7）。但 5 个进程的 seq 0..n 互相「重投」，后到的整批丢弃——它们不是重投，是
   不同进程的不同请求。

即：协议假设「一次上报 = 一个进程」，xdist 打破了这个假设。

## 修法（已实施，全部在 apitrack-sdk-python）

平台侧一个字都没改：`(run, seq)` 的去重是冻结协议 v1.0 的幂等语义，平台无法区分「同批
重投」与「另一进程的巧合同号」——按协议该丢弃。修法是**把那条假设恢复成事实**：让一次
运行重新只有一个进程上报，而不是教平台去合并 N 份。

新增 `apitrack/distributed.py`（进程角色判定 + 交接通道），改 `collector.py` 与
`plugin.py`：

- **worker 不上报，交回 controller**：worker 在 `sessionfinish` 里把自己采到的
  cases/records/filters/warnings 挂进 xdist 自己的 `config.workeroutput`（`hand_off`），
  然后直接 return。controller 在 `pytest_testnodedown` 里取出并 `Collector.absorb` 合并，
  于是它在自己的 `sessionfinish` 时手上是完整的一份。这是 xdist 为「worker 有数据要带
  回来」提供的机制（pytest-cov 用的也是它），随 worker 的 `sessionfinish` 送达，而
  controller 的 `pytest_runtestloop` 要等所有节点 down 才退出，次序有保证。
- **合并复用既有入口**：`absorb` 走 `register_case` / `set_result` / `add_record`，不另写
  一套 merge——「一个子项失败就是整条用例失败」「标签取并集」「超上限只丢 records」因此在
  单进程与多进程下由同一段代码决定。`unknown` 结果**跳过**不参与合并：xdist 的每个 worker
  都 collect 全量、只跑一部分，没跑到的那些结果是 `unknown`，让它进 `set_result` 会让答案
  取决于 worker 的到达顺序。
- **worker 侧的过滤要带回来**：deselect 发生在 worker 自己的 collect 里，controller 身上
  永远不会触发 `pytest_deselected`。`export_slice(filters=…)` 把它带回、`_note_filter`
  并进 controller 的 filters，否则一次「只跑 2 条」的勾选执行会被报成范围内的全量，平台
  照它把树上其余用例全判成消失。
- **收不到就不声明全量**：worker 崩了（`--max-worker-restart 0` 后 `errordown`）或它走了
  降级路径，controller 就少一批用例，`is_full_inventory` 强制为 false。
- **一份都没收到时一个字都不发**：controller 不 collect、手上是空的，而 `case_total` /
  通过失败数是平台侧「每次重算」的列——发一份空 payload 恰好会把 worker 刚报上去的计数
  覆盖成 0（现象里的第二个症状）。改成打一行说明直接返回。
- **降级路径（很老的 xdist 没有 `workeroutput`）**：退回「每个 worker 各发一份」，但
  `Collector.seq_base` 按 `gw 序号 × 1_000_000` 给每个进程一个不交叠的 seq 段（段宽远大于
  本地与平台两侧的 20 000 上限），批次内重投仍幂等、进程间不再碰撞；同时记一项
  `xdist-worker` 过滤，那几份都不声明全量。
- **身份只认 `config.workerinput`，不认 `PYTEST_XDIST_WORKER`**：后者会被**测试自己起的
  pytest 子进程**继承（这个仓库的集成测试就是这么跑的），认它会让那种子进程把自己当
  worker、交接失败、然后把一次本该正常的单进程上报报成非全量。
- **`pytest_testnodedown` 必须带 `optionalhook=True`**：它是 xdist 自己加的 hookspec，
  没装 xdist 的环境里不存在，而 pytest 在 collect 结束时调 `pluginmanager.check_pending()`
  会把「实现了一个没人声明的钩子」判成 `PluginValidationError`——那会让每一个没装 xdist 的
  用户装上这个包后 pytest 直接起不来。已在无 xdist 的干净 venv 里验过。
- **`-n0` / `--dist no` 按单进程走**：controller 判据是「`dsession` 这个插件在不在」而不是
  `-n` 的取值，xdist 只在真要分发时才注册它。

顺带修掉两处：`sessionfinish` 在停用状态下提前返回（不再为每个 worker 白跑一次 execnet
序列化）；集成测试的子进程命令补 `-p no:apitrack`，否则开发机上装着的旧包与源码树那份会
同时加载，pytest 直接报 `Plugin already registered under a different name` 让整个文件全红。

## 验证

`tests/` 从 41 条加到 48 条，全绿。新增的 xdist 组是真起多进程的集成测试（缺陷本体就是
「进程数 > 1」，单进程 mock 里不存在）：只上报一份、合并后与单进程逐字段相同、seq 从 0
密集唯一（12 条一条不丢）、worker 侧 deselect 传到 controller、collect 报错降级、`-n0`
等价单进程、崩掉一个 worker 后不声明全量。另用一个本地 stub `/ingest` 端到端确认：正常
路径 1 次请求 / 12 条 records / seq 0–11；模拟老版本 xdist 时 3 份各自落在 0、1e6、2e6 段
且 controller 不再发那份空的。

`pytest-xdist` 进了 `dev` extra 与 CI 的 `test` job——可选依赖 + skip 的组合能让一条性质
在 CI 上永远绿着却从未被执行。

## 状态

已修复（apitrack-sdk-python，未发版）。修复前的临时规避（任务命令 `-p no:xdist`）不再需要。
**已随 2026-09-03 P4.5 验收通过关闭**（该修复在 SDK 侧，平台未发版不影响平台侧验收；
下个 SDK 版本发布时随版上线）。
