## 缺陷 1：任务列表的在途状态从落地那天起从未显示

**现象**

仓库任务列表行内的「执行中 / 排队中」状态词 + `#序号` 从来没出现过，即使有 run 正在跑。
P4.5 走查五项的第 ⑤ 项（`issue_fix/问题记录-P4.5仓库模式走查五项.md`）声称已修，行为上没修。

**根因**

`routes/ciTasks.ts` 的列表查询是把两段 `LEFT JOIN LATERAL` 接在常量 `TASK_SELECT` 后面拼出来的：

```ts
const TASK_SELECT = `SELECT t.*, c.name AS git_credential_name, c.method AS git_credential_method
   FROM ci_tasks t LEFT JOIN git_credentials c ON c.id = t.git_credential_id`;

pool.query(`${TASK_SELECT}
  LEFT JOIN LATERAL ( SELECT COUNT(*)::int AS active_run_count, ... ) ar ON true
  WHERE ...`);
```

join 只决定**行**，投影只看 **SELECT 列表**。`TASK_SELECT` 的列表是
`t.*, c.name, c.method` —— `t.*` 只展开 `ci_tasks` 的列，`ar.*` 一列都没进结果集。于是
`mapCiTask` 读到的 `row.active_run_count` 恒为 `undefined`，按 mapper 里那条刻意的语义
（「缺列 = 未知，不与『没有在途』混同」）落成 `activeRun: undefined`，界面据此什么都不渲染。

在本机 dev 库上验证过（只读）：

```
-- TASK_SELECT + LATERAL 的返回列
id, project_id, name, ..., git_credential_name, git_credential_method
has active_run_count? false

-- 逐列写全之后
纯测试  active: 0 null | last: #11 failed | total: 11
```

`t.*` 遮蔽了这个错误：查询能跑、不报错、行数也对，只是多出来的列静默消失——与
`问题记录-P4.5-13执行详情页四处前端缺陷` 里那几个「静默失效」同一类失败模式。

**修法**

列表路由不再复用 `TASK_SELECT`，改为自己的 SELECT 并**逐列写全**两段 LATERAL 的输出：

```sql
SELECT t.*, c.name AS git_credential_name, c.method AS git_credential_method,
       ar.active_run_count, ar.active_run_id, ar.active_run_number, ar.active_run_status,
       lr.run_total, lr.last_run_id, lr.last_run_number, lr.last_run_status
  FROM ci_tasks t
  LEFT JOIN git_credentials c ON c.id = t.git_credential_id
  LEFT JOIN LATERAL (...) ar ON true
  LEFT JOIN LATERAL (...) lr ON true
 WHERE ...
```

`TASK_SELECT` 的注释同步改成「详情 / 创建 / 更新的读取形状」——列表页的投影与它们不同，
就让它有自己的 SELECT，而不是留一个「看起来能复用」的陷阱给下一次。

**状态**：已修（`apitest-server/src/routes/ciTasks.ts`）。同一次改动补了 `lastRun` /
`runTotal` 两列，那是新功能（开发计划 8.14 的 ⑦）。

## 缺陷 2：报告用例明细里的步骤树 caret 是装饰，点不动

**现象**

用例展开后，步骤树每行前面都有一个 `▾` / `▸`，看起来可折叠，点下去没有任何反应。一个循环
或子流程产生的几十上百个嵌套步骤永远全展开，把展开区撑到几屏高。

**根因**

`StepTree` 用 caret 的**朝向**表达「这一支有没有子步骤」，而不是「展开还是收起」：

```tsx
{step.children?.length ? <ChevronDown size={13} /> : <ChevronRight size={13} style={{ opacity: 0.3 }} />}
...
{step.children?.length ? <StepTree steps={step.children} ... /> : null}   /* 无条件递归 */
```

没有任何折叠状态，子树永远渲染。`.step-row` 是 `<span>`，也没有点击目标。

**修法**

拆出 `StepNode`，自持 `open`（默认展开——步骤是「执行了什么」的主线，收起来读不到）；有子
步骤的行渲染成 `<button className="step-row" aria-expanded>`，整行可点、键盘可达；没有子步骤
的行仍是 `<span>`，caret 用 `.step-caret[data-leaf]` 置灰表达「这是叶子」。

**状态**：已修（`apitest-web/src/components/PipelineRunPage.tsx`、`design-system.css`）。

## 复核后判定不改

**「报告里看不到步骤日志」不是平台缺陷。** 反馈第 ⑩ 项报的是「日志有收集的话应该展示出
来」。核对过：平台**一直**会展示——`StepTree` 渲染 `step.attachments`，`AttachmentView` 把
文本类附件就地读出来。日志缺席的原因在任务命令里：

```
pytest test_case/ --reruns 1 --reruns-delay=2 --alluredir ./allure-results --clean-alluredir --allure-no-capture
```

`--allure-no-capture` 正是「不要把 pytest 捕获的 logging/stdout/stderr 附到报告上」
（`allure_pytest/plugin.py` 的 `attach_capture`）。本机现存的七个报告包里附件数都是 0，与之
一致。

界面侧的真实缺陷是**没有解释这个缺席**：一个没有任何附件的报告读起来像「平台没收集日志」。
因此这一项按「补一条说明」处理——报告包附件清单为空时，报告主体显示
`pipelineRun.noAttachmentsHint`，把原因与处置（去掉那个参数）说清。同时把测试级的
`log`/`stdout`/`stderr` 从「附件」拆成「执行日志」块并默认展开，这样下次带上日志时它在第一
眼的位置，而不是要点两下才看到。

**状态**：说明已补（开发计划 8.14 的 ⑩）；无平台侧行为缺陷。
