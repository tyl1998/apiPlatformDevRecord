# P4.5 仓库任务产物直传全链路失效（报告视图 / 产物 / SDK 上报）

## 现象

任务「纯测试」的命令带 `pytest … --alluredir ./allure-results`，执行成功、用例计数正常
（`report: parsed 35 allure file(s) → 35 case(s)`），但执行详情页：

1. **报告视图** tab 恒空（`GET /pipeline-runs/:id/report` 回 `data: null`）；
2. **产物** tab 恒空；
3. artifacts 表里躺着一行 `kind='report'`、`size_bytes=28672`、**`uploaded_at IS NULL`** 的
   申请记录——字节从没传上来过；
4. 仓库模式开了「注入 SDK 上报变量」，但上报记录页没有任何新 run，job 日志里只有 SDK 的
   告警 `apitrack skipped reporting: could not determine the git remote or commit`；
5. Runner 侧看不到任何上传失败的线索（api.log 里连 PUT 请求都没到）。

## 根因

五个缺陷叠在同一条链上，前三个每个单独都能让产物传不上来：

1. **直传地址丢端口（主因）**。三处拼平台对外地址用的都是
   `${request.protocol}://${request.hostname}`，而 Fastify 的 `request.hostname`
   **刻意剥掉端口**：Runner 拿到的 `upload_url` 是 `http://localhost/runner/artifacts/…`
   （80 端口）。实测复现：`fetch` 直接 `ECONNREFUSED ::1:80 / 127.0.0.1:80`，三次重试
   全灭，`upload_url` 的申请却成功了——所以 artifacts 行存在、字节永远不来。受影响的
   三处：产物直传地址（`runners.ts`）、产物下载直链（`pipelineRuns.ts`）、JobSpec 的
   `APITRACK_URL`（`runners.ts` claim 路由——SDK 上报地址同样拨 80）。
2. **直传路由的 content-type 解析器把流吃掉了**。
   `addContentTypeParser("application/octet-stream", { parseAs: "buffer" }, …)` 会把
   `request.raw` 读完才进 handler，而 handler 靠 `pipeline(request.raw, …)` 落盘——
   实测：带正确 content-type 直传返回 200 `{size_bytes: 0}`，写出来的是 0 字节文件、
   checksum 是空串的 sha256。注释写的「不解析、直接放行」与实现相反。
3. **fs 的 presignPut 不下发 content-type**。Runner 原样转发 `target.headers`（只有
   token 头），undici 对 Uint8Array body 不自动补 content-type，直传端点只给
   `application/octet-stream` 注册了解析器 → Fastify 415。s3 分支一直有这个头，fs 漏了。
4. **终态后日志被 409 吞掉**。Runner 的收尾顺序是 complete → 传产物，产物上传的成败行
   （`report-bundle: upload failed (…)`）必然落在终态之后；而 `appendPipelineRunLogs`
   按 ACTIVE_GUARD 拒收（路由回 409「no longer active」），streamer 静默放弃——失败
   原因永远进不了 job 日志，这就是「看不到任何线索」的原因。路由注释里写的
   「终态后仍收（回 ok）」与实现矛盾。
5. **SDK 的仓库身份探测注定失败**。Runner 的 clone 是 init + fetch + checkout、刻意不
   `git remote add`（https_token 的地址带凭据，落进 workspace 的 `.git/config` 就活到
   任务结束），workspace 里没有 `remote.origin`，SDK 的 `detect_git_url()` 拿不到、
   整个上报跳过（它的告警原文就叫人设 `APITRACK_GIT_URL`）。平台没注入这个变量。

## 修法

- `lib/objectStore.ts`：新增 `requestBaseUrl(request)`——`PUBLIC_BASE_URL` 优先，缺省取
  **Host 头原样**（带端口）；三处调用点（runners.ts ×2、pipelineRuns.ts）全部换过去。
- `lib/objectStore.ts`：fs `presignPut` 的 headers 补 `content-type:
  application/octet-stream`（产物逻辑类型记在 artifacts 表，不上线路）。
- `routes/runners.ts`：直传解析器去掉 `parseAs: "buffer"`，改流式透传
  （`done(null, body)` 不指定 parseAs 时 body 就是原始流，归 handler 消费）。
- `lib/pipelineRun.ts`：`appendPipelineRunLogs` 去掉 ACTIVE_GUARD 拒收（归属
  `runner_id` 仍是硬判据，FOR UPDATE 锁行保证与终态写入不交错），路由删掉对应 409
  分支——与注释承诺的「终态后仍收」对齐。
- `lib/jobSpec.ts`：`sdk_ingest_enabled` 时注入 `APITRACK_GIT_URL = task.git_url`
  （四件套之三 URL/TOKEN/CI_RUN_ID 之外的第四件）。

用平台真实 runner token + dist 产物做了三层实测定位：无端口的 `upload_url` 稳定复现
`ECONNREFUSED 80`；手工把端口补回后 content-type 缺失复现 415；带 content-type 又复现
`size_bytes: 0`。本地 Fastify 最小例验证流式透传后 `request.raw` 可完整读到字节。

## 状态

已修复（server 五处）。Run #3 那行 `uploaded_at IS NULL` 的申请记录已无文件对应、各读取
路径都按 `uploaded_at IS NOT NULL` 过滤，不挡新产物；原「跑一次新 run 即可拿到报告
视图」——**已随 2026-09-03 P4.5 验收通过关闭**。Runner 侧零改动（URL 与 headers 都由
平台下发）。
