# 问题记录-勾选执行落库键形不匹配致全量跑

- 日期：2026-09-03
- 阶段：P4.5-9 勾选用例快速执行（§8.3）
- 状态：**已修**（服务端 `lib/trigger.ts` 一处；dev 库旧行未回填，直接重触发即可）

## 现象

仓库用例树上勾选若干用例 → 触发 CI 任务 → 仓库脚本**全量跑**（勾 7 条、实际跑了
40 条：`4 workers [40 items]`，25 passed + 15 skipped）。执行详情页 job 日志的
`job started: run #24, sandbox process, timeout 1800s` 一行**没有** `case filter N key(s)`
尾段；run 终态后树上也没有任何 `not_run` 差集标记——勾选执行的整条链路（筛选注入、
not_run 兜底）静默失效。

## 根因

`case_filter` jsonb 的**写读键形不一致**（一个 camelCase、其余全部 snake_case）：

- **写入侧** `lib/trigger.ts` 的 `normalizeCaseFilter` 返回 `{ caseKeys: [...] }`
  （camelCase），`INSERT INTO pipeline_runs ... case_filter` 原样落库；
- **读取侧** 共 4 处全部按 snake_case `case_keys` 读：
  - `lib/jobSpec.ts:202`（claim → JobSpec）：`run.case_filter.case_keys` 是
    `undefined` → `Array.isArray` 为 false → 兜底 `{ case_keys: [] }` **空数组**；
  - `lib/pipelineRun.ts` 的 `caseFilterKeys`（complete / 租约回收两处 not_run 差集
    对账）：读出 0 个 key → 对账直接跳过；
  - `models/types.ts` 的 `mapPipelineRun`（run 详情 API 的 `caseFilter` 恒空数组）。

于是 Runner 拿到 `case_filter = { case_keys: [] }`：`executor.ts` 的
`keys.length` 为 0，既不注入 `APITRACK_CASE_KEYS`，job 日志的 `case filter` 尾段也不
打印（两处共用同一个 falsy 判定）——SDK 端 `resolve_case_keys` 收不到 env，按「没有
选择」走全量，行为完全「正确」，问题全在平台侧把 key 弄丢在半路。

顺带说明为什么此前没暴露：`execution_index` 的「只看勾选来的」筛选（`case_filter IS
NOT NULL`）只判 NULL 不看键名，碰巧能用；勾选执行的 SDK 端到端测试
（`test_plugin_session.py`）是**直接设 env** 绕过了平台注入这一段。

## 修法

`lib/trigger.ts` 一处：`normalizeCaseFilter` 的返回值改为 `{ case_keys: keys }`
（snake_case），并同步改掉审计日志 `caseFilterCount: caseFilter?.case_keys.length`。
请求侧键名 `caseKeys`（camelCase 信封）保持不变——归一函数就是做这个翻译的地方。
读侧四处的 snake_case 形状本来互相对齐，不动。

判「干净优先」不写兼容读：项目从未发布，无历史数据要保；dev 库里 run 24 那行的
camelCase 旧值直接作废（重触发即产生新行）。

## 验证路径（留给下次触发）

1. 触发勾选执行 → 执行详情页 job 日志首行出现 `case filter N key(s)`；
2. pytest 终端摘要出现 ` deselected` 与实际条数（勾 7 → 40 collected / 33 deselected /
   7 selected）；
3. run 终态后树上未报到的勾选 key 落 `not_run`（差集对账恢复）。
